**Status:** AUTHORIZED BOUNDED RESEARCH PLAN — position-neutral; `MEMORY.md` alone selects live continuation  
**Responsibility:** execute the delegated product-simulation research needed to determine where a bounded LLM planner/controller can add material value beyond fixed or mechanism-specific deterministic sequencing

**Primary main-facing deliverable:** `working-memory/2026-08-28_B2-X1-product-simulation-capability-research-response.md`  

## 1. Purpose

This plan coordinates one consequential research responsibility:

> Find real, evidence-backed situations in realistic dependency-update investigations where a bounded LLM planner/controller can add material value over a small fixed/mechanism-specific deterministic policy, while deterministic UpgradePilot owners retain source identity, action authority, execution, evidence interpretation/promotion, proof strength, security boundaries, and final trusted state.

The plan exists because this responsibility is now broader than one bounded pressure test. It may require:

- inspecting several existing product/simulation responsibilities;
- rejecting superficially attractive but deterministically trivial planner actions;
- identifying one or more independently justified read-only capability families;
- finding real cases with meaningful choice, prerequisites, prioritization, sequencing, failure/staleness, or stopping pressure;
- separating design-research cases from possible future holdout material;
- preserving barriers, failed methods, evidence limits, and negative results;
- returning an auditable recommendation to main before main chooses the next planner responsibility or freezes a fresh v3 evaluation.

This is an **investigation/execution plan**, not a product architecture specification, not a v3 evaluation protocol, and not a live-state owner.

Main has already established enough evidence to distinguish several planner/control responsibilities:

The evidence-refined first seam is a **control contract**, not the desired upper bound of planner power.

### 3.2 Deterministic authority remains outside the planner

- exact repository / PR / immutable revision identity;
- admitted capability catalog;

- capability execution authorization;
- evidence parsing and deterministic interpretation;
- evidence promotion and proof-strength composition;

`acquire_exact_target_python_declaration` is a real and useful first action, but the deterministic product already knows how to select it in the simplest S001 state.

Therefore this research must not justify the planner merely by reproducing that one deterministic rule.

### 3.4 Existing simulation transfer findings remain useful pressure dimensions

Current branch evidence already established:

- no-tool semantic correctness is separate from tool safety;
- selection-time validity is separate from execution-time validity;
- fresh trusted state can invalidate a previously valid action;
- planner-level blind-repeat suppression is separate from deterministic transport retry;
- typed domain/evidence problems are separate from transient acquisition failures.

Use these as pressure dimensions when richer capability candidates naturally encounter them. Do not keep extending them as independent work merely to accumulate more documents.

## 4. Research outcome and decision this plan must enable

The research is complete when main can make an evidence-backed decision among paths such as:

```text
A. one or more richer planner responsibilities are justified
→ main may design the smallest strong action/state expansion
→ only after that, main may freeze an appropriate fresh v3 evaluation

B. useful model reasoning exists, but executable capability expansion is not yet justified
→ main may narrow the honest planner claim to prioritization / sequencing / defer / stopping
→ or identify the missing capability evidence needed next

C. no material planner-value expansion is justified
→ do not manufacture capability
→ main decides whether to retain the first seam as a limited pilot, defer X1, or reject expansion
```

A valid research result may therefore be **zero promoted capabilities**.

The goal is not to prove that an LLM planner must exist. The goal is to identify the most valuable honest responsibility, if any.

## 5. Core research principles

### P-01 — powerful and evidence-backed, not minimal for minimalism

Do not optimize for the fewest mechanisms or actions.

Complexity may be justified when it buys real capability, for example:

- meaningful choice among several useful investigations;
- adaptive sequencing across evidence states;
- cross-responsibility prioritization;
- better handling of failed/stale attempts;
- bounded budget / information-value reasoning;
- stronger observability/replay;
- useful failure/abstention behavior;
- meaningful AI/LLM engineering capability and learning value.

Reject complexity that is redundant, ceremonial, speculative, or merely makes the system appear agentic.

### P-02 — compare against the strongest simple deterministic baseline

For every serious capability/planner-state candidate ask:

> Could a small deterministic rule or fixed sequence select the same next step across the realistic supported state space with equal clarity and lower complexity?

If yes, deterministic ownership is normally preferred.

The LLM earns planner responsibility when the policy becomes materially contextual, cross-responsibility, combinatorial, semantically rich, or brittle under fixed rules.

### P-03 — actions must be independently justified

Do not invent an action because multi-action planning would make a better demo.

A candidate planner-visible action must correspond to a recurring, bounded investigation responsibility that has evidence value independent of the planner experiment.

### P-04 — bound the supported domain, not the known case

Cases are evidence/pressure. They are not product semantics.

Do not define a capability as:

```text
if repository == X
or case == S00N
then perform Y
```

A serious candidate must have a credible responsibility boundary that can generalize across relevant variation inside UpgradePilot's supported domain.

### P-05 — planning value is information value, not tool count

Two actions are not automatically more agentic or valuable than one.

Research should identify whether the planner must reason about:

```text
which uncertainty matters now?
which available investigation discriminates it best?
which prerequisites are already satisfied?
which action is redundant/stale/previously failed?
what does the remaining budget allow?
when should investigation stop/defer/remain unresolved?
```

### P-06 — design research and final evaluation evidence are different uses

A case used to shape the action space, prompt, state representation, or reasoning policy is no longer safely assumed to be untouched final protected evidence.

Preserve this distinction explicitly.

### P-07 — progressive evidence preservation, not documentation ceremony

Record material:

- observations;
- exact case identities;
- evidence acquired;
- failed/inaccessible methods;
- barriers and workarounds;
- interpretation;
- claim limits;
- candidate promotion/rejection reasons;
- contamination/exposure state;
- stopping decisions.

Do not create a new document after every lookup. Preserve state where losing it would harm auditability, continuation, or main's decision.

## 6. Case-use and contamination discipline

Maintain an explicit **case-use ledger** during research. It may live inside the evolving main-facing response or a small supporting research record if the work becomes too large for one file.

Use these classifications:

### `historical_consumed`

Case has already been materially used by v2, E1–E5, prior prompt/design tuning, or current simulation transfer work such that it must not be represented as untouched final v3 evidence.

Use freely for design learning, mechanism discovery, and counterexamples while preserving provenance.

### `design_research_used`

A previously fresh/new case has been inspected deeply enough to shape capability/action/state/prompt/design reasoning.

It remains valuable research evidence but should not later be described as untouched protected evidence.

### `screened_only`

Case identity/basic suitability was inspected only far enough to decide whether deeper research is warranted.

Record exactly what was viewed. Do not assume this classification automatically qualifies the case for future protection; main's eventual v3 protocol must judge exposure/contamination.

### `reserved_holdout_candidate`

A plausible fresh case has been deliberately left materially uninspected after minimal identity/suitability screening so main can later decide whether it should become protected v3 material.

This plan does **not** freeze it as protected evidence.

### `rejected_or_unsuitable`

Case was rejected for planner research because it is outside scope, unsafe, too trivial, too ambiguous, unsupported, already consumed, or not discriminating.

Preserve the reason when it prevents repeated rediscovery.

### Case-use rules

1. Never call a case "fresh protected" in this research plan/output.
2. Do not inspect a reserved holdout merely to satisfy curiosity.
3. If deeper inspection becomes necessary, reclassify it to `design_research_used` before using the outcome to shape design.
4. Do not reserve all good cases; capability design needs real evidence.
5. Do not consume all good cases either; preserve enough untouched material for main to construct a meaningful future evaluation if the candidate proceeds.
6. For S001–S012, use the explicit contamination/history mapping from the main handoff rather than guessing.

## 7. Candidate capability admission test

A capability is a **serious planner-visible candidate** only if the research can answer all applicable questions below with evidence.

### C-01 — planning uncertainty

What exact unresolved proposition/question does the capability discriminate?

### C-02 — evidence output

What exact evidence/result/problem family would the capability acquire or produce?

### C-03 — deterministic inputs/locators

Which repository/revision/path/environment/configuration/command identity can remain deterministically pre-bound rather than generated by the model?

### C-04 — bounded effect

Is the capability read-only or otherwise safely bounded inside the authorized research/product horizon?

### C-05 — existing owner

What UpgradePilot module/responsibility already owns all or part of the capability? Is a new owner actually missing?

### C-06 — recurrence/generality

Does the responsibility recur across realistic cases, or is it one-off scenario logic?

### C-07 — simple-rule baseline

Would a small deterministic condition/fixed sequence select this capability correctly in the relevant realistic states?

### C-08 — planner-value pressure

What becomes difficult, brittle, combinatorial, semantically contextual, or over-investigative if deterministic fixed orchestration owns selection?

### C-09 — engineering/learning value

What real AI/LLM/agent-engineering responsibility would this expose, for example:

- action-space reasoning;
- prerequisite/dependency planning;
- information-gain prioritization;
- budgeted planning;
- stateful multi-turn orchestration;
- stale-plan handling;
- tool-result/failure-aware replanning;
- abstention/stopping;
- structured tool selection;
- trace/replay/evaluation.

Learning value strengthens an already-real capability case; it does not create product necessity by itself.

### C-10 — authority / claim limit

What is the strongest fact the capability may establish, and what remains outside its authority?

If the answer to C-07 is consistently "yes, a small deterministic rule is equally good" or C-06 is "one-off", reject planner exposure unless another independent responsibility changes that conclusion.

## 8. Research lenses — hypotheses, not pre-approved actions

Use these as discovery lenses only. Promote none without the candidate admission test.

### L-01 — exact environment / package-resolution evidence

Potential questions:

- Does an exact target environment admit the proposed dependency set?
- Does resolution expose a family/platform/marker conflict not visible from source declarations alone?
- When is static package metadata already sufficient, making a resolver run redundant?

Planner value may arise if several evidence paths exist with different costs and prerequisites.

### L-02 — mediated CI / runner / environment consumption

Potential questions:

- Which workflow/test environment actually consumes the changed dependency declaration or lock/root?
- Is direct workflow evidence enough, or is tox/nox/script/config mediation material?
- Which exact configuration read has the highest information value next?

This is promising only if deterministic orchestration would otherwise require many mechanism-specific branches.

### L-03 — targeted behavioral/reproduction differential

Potential questions:

- Static evidence maps a plausible behavior change to target code, but does the affected branch behave differently across the old/new dependency versions?
- Is a bounded existing reproduction/check available?

This capability has higher execution/sandbox/untrusted-code risk. Research its value and boundary without assuming it is admissible as an early executable action.

### L-04 — artifact/provenance history

Potential questions:

- Did a persisted/generated artifact originate under the old dependency state and survive into the proposed update context?
- Can repository/CI/release metadata establish that provenance without executing unknown code?

May often support `defer` rather than an executable planner action if the required history lives outside supported evidence channels.

### L-05 — repository-purpose / reproduction-context evidence

Potential questions:

- Does the repository/configuration serve as a reproduction fixture, generated environment, test substrate, or production path?
- Does that context change which evidence is technically relevant?

Purpose/provenance context may guide investigation prioritization but must not become compatibility proof by itself.

### L-06 — upstream mechanism/candidate discovery

Potential questions:

- One dependency transition contains several materially different upstream change mechanisms; which candidate requires target investigation?
- Has one mechanism been found while discovery remains incomplete?

This may be a separate semantic-discovery model responsibility rather than a planner action. Do not collapse extraction and planning merely because both use an LLM.

### L-07 — exact source/configuration acquisition for cross-domain gaps

Potential questions:

- Which one of several pre-bound target configuration sources would best resolve the active proposition?
- Is the choice contextual enough to justify planner selection rather than deterministic traversal?

The action should expose a meaningful investigation purpose, not arbitrary file-read authority.

# R2 — Planner-value discrimination against deterministic baselines

## Question

For each serious candidate, is LLM selection/sequencing materially better justified than a small deterministic rule or fixed mechanism-specific sequence?

## Actions

For each surviving candidate:

1. write the strongest simple deterministic baseline;
2. identify realistic state dimensions that affect the next action, such as:
   - proposition relevance;
   - prerequisite satisfaction;
   - several simultaneously available actions;
   - cost/information value;
   - attempt history;
   - stale action/state;
   - typed domain problem versus transient acquisition failure;
   - remaining step budget;
   - outside-but-known capability causing `defer`;
   - settled bounded question causing `stop`;
3. estimate whether fixed rules remain small, stable, explainable, and complete across those states;
4. identify where rule count/ordering becomes mechanism-specific, brittle, combinatorial, or semantically contextual;
5. separate model **planning value** from model **semantic extraction value**;
6. reject candidates where the LLM would merely echo an obvious deterministic selector.

## Useful comparison shape

```text
candidate state dimensions
→ strongest deterministic policy
→ model-planner responsibility
→ what changes in supported behavior / flexibility / maintainability
→ failure/authority consequences
→ evidence still needed
```

## Gate R2

A candidate becomes a **serious capability hypothesis** only if a real planner-value distinction remains after the deterministic-baseline comparison.

If the distinction exists only because the deterministic baseline was intentionally made weak, reject the conclusion.

# R3 — Targeted fresh-case discovery and screening

## Question

Can untouched public dependency-update cases provide better external evidence for the surviving capability hypotheses and later evaluation needs?

## Entry condition

Do not browse randomly for cases before R1/R2 define what evidence would discriminate the candidate.

## Search strategy

Search for cases with evidence features relevant to the surviving hypothesis, for example:

- multiple environment/configuration layers;
- optional extras and workflow matrices;
- tox/nox/script-mediated installation;
- lock/resolver/platform interactions;
- persisted/generated artifacts;
- upstream changes with multiple independent mechanisms;
- target code paths plausibly requiring a bounded differential check;
- several reasonable read-only evidence acquisitions whose order matters.

Prefer supported-boundary public Python dependency-update/Dependabot cases when practical, but do not force a case that does not answer the research question.

## Screening discipline

For each candidate public case record only what is necessary to decide among:

```text
reject
screened_only
promote to design_research_used
reserve as holdout candidate
```

Do not deeply inspect every attractive case.

### Holdout reservation heuristic

Reserve a case when:

- its visible identity/basic metadata suggest it could pressure a candidate responsibility;
- another design case can answer the current architecture question sufficiently;
- deeper inspection is not required yet;
- preserving an untouched/low-exposure example would materially help a future v3.

This is a research reservation, not protocol freeze.

## Gate R3

Proceed to deep case investigation only when the case is expected to change candidate promotion/rejection, clarify a planning-state distinction, or establish that a capability is recurring/general.

# R4 — Deep case investigation / controlled simulation

## Question

Do real case facts actually support the proposed capability/planner-value mechanism?

## Evidence form priority

Use the least artificial evidence form that answers the question:

```text
untouched real case
→ captured real fixture
→ real-derived controlled variant
→ mock/fake for interaction/failure branches
→ synthetic/property-based only when necessary
```

## Actions

For each admitted design-research case:

1. freeze exact repository / PR / revision and observation time where material;
2. state the exact planning uncertainty;
3. identify the transparent deterministic baseline/current product behavior;
4. acquire only the evidence needed to discriminate the candidate capability;
5. preserve failed/inaccessible methods rather than replacing them silently;
6. separate:
   - observation;
   - deterministic transformation;
   - interpretation;
   - hypothesis;
   - recommendation;
7. identify any real competing actions, prerequisites, sequencing, cost, history, stale/failure, or stopping pressure;
8. stop early when stronger evidence already resolves the question;
9. do not mutate/comment/approve/rerun/merge target repositories;
10. do not execute unknown target code merely to make a candidate more interesting.

## Controlled-variant rule

Use a controlled variant only when one variable must change to isolate a planner mechanism and the real case cannot provide that contrast safely/cleanly.

Do not let a synthetic expected answer become circular proof of planner value.

## Gate R4

Promote a capability for main-side design study only when real/captured evidence shows:

- recurring/plausibly recurring responsibility;
- non-trivial planning value over the strongest simple deterministic baseline;
- bounded evidence authority;
- a credible action/result boundary or an honest no-tool/sequencing responsibility;
- useful generality beyond one known fixture.

Otherwise reject or narrow it explicitly.

## 11. Planner-value heuristics to challenge explicitly

Reject or pressure-test these common shortcuts:

### H-01 — "more tools means more planner value"

False. Tool count is not information-value complexity.

### H-02 — "anything unresolved means continue"

False. Adjacent/deeper unresolved facts may be irrelevant to the bounded question.

### H-03 — "the first available action should always run"

False. A later/cheaper/more discriminating action may dominate, or the action may be stale/redundant.

### H-04 — "a failed action should always be retried/replanned"

False. Typed domain problems and transient acquisition failures have different owners/semantics.

### H-05 — "if several deterministic `if` statements can encode one case, LLM planning is unnecessary everywhere"

False unless those conditions remain small/stable across the realistic responsibility horizon. Evaluate the whole bounded responsibility, not one fixture.

### H-06 — "cross-domain reasoning should move evidence truth into the model"

False. The planner can reason over typed trusted state while deterministic owners retain fact/proof authority.

### H-07 — "a rich planner is justified because it is educational"

False. Learning value is additive only after a real product responsibility exists.

### H-08 — "a new case is useful because it fills a disposition/action label"

False. Admit cases for material uncertainty, not label quotas.

## 12. Research stopping rules

### Stop a candidate capability investigation when

- a small deterministic policy clearly owns the realistic states better;
- the capability is one-off case logic;
- safe/read-only bounding is not credible for the current horizon;
- evidence authority would have to move improperly into the model;
- repeated cases add no new planner-value distinction;
- another investigation is unlikely to change promote/reject/narrow disposition;
- the useful next responsibility is outside supported capabilities and the honest result is `defer`.

### Stop a case investigation when

- decision-critical evidence is already sufficient;
- additional facts address only deeper/adjacent questions;
- the next check would require unsafe or unauthorized target execution/mutation;
- evidence is inaccessible and the uncertainty/claim limit is already clear;
- more acquisition would not change the candidate capability conclusion.

### Stop the whole research program when

main has enough evidence to choose the honest next planner responsibility, specifically when either:

```text
1–3 strong candidates are sufficiently characterized
and further cases are unlikely to change their relative recommendation
```

or:

```text
no candidate survives the independent-capability + planner-value gates
and the missing evidence needed to change that conclusion is explicit
```

Do not continue until the research feels exhaustive.

## 15. Reassessment triggers

Reassess this plan rather than mechanically continuing when:

- main materially changes the B2/X1 owning question or authority split;
- a new accepted specification/ADR changes the supported product horizon;
- a discovered capability requires a different trust/execution class than read-only bounded investigation;
- case contamination leaves insufficient credible holdout material for future evaluation;
- two substantial research slices in a row add cases/details without changing any candidate disposition;
- a candidate's deterministic baseline becomes clearly sufficient and removes the planner-value question;
- a previously unavailable capability becomes implemented on main and materially changes the action-space evidence.

A reassessment may narrow, reorder, or stop research. Do not expand the plan merely because new ideas appear.

## 16. Recommended research rhythm

For each substantive slice, use the project Learning-by-Doing method proportionately:

```text
1. identify one capability/planner-value question
2. orient on the exact owner/evidence needed
3. perform bounded inspection/simulation
4. inspect actual evidence
5. preserve material findings/barriers/exposure state
6. explain what changed and what did not
7. decide promote / reject / narrow / investigate-next
8. continue only if the next evidence can change the recommendation
```

This plan should make the research recoverable across sessions without converting every step into ceremony.
