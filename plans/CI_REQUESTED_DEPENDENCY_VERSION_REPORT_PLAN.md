# Report explicit dependency version requests in CI workflows

This bounded plan serves the maintainer question **why do these green CI jobs leave the proposed dependency version unverified?** The [OmniMatch report trace](../working-memory/2026-11-10_omnimatch-ci-report-evidence-trace_cycle.md#where-the-explanation-stops) supplies a normal CI preparation baseline. Two workflows explicitly request HTTPX 0.27.0 while the PR proposes 0.28.1. Existing CI coverage correctly records that changed-dependency consumption was not established. The raw YAML survives Workspace reconstruction and the report links to it.

Use the [maintainer utility route](PRODUCT_DIRECTION_AND_MAINTAINER_UTILITY_INVESTIGATION_PLAN.md#task-first-reassessment-after-delivered-reports), [Core report and provenance rules](../docs/specifications/UPGRADEPILOT_CORE_PIPELINE_AND_CONTRACT_SPECIFICATION.md#61-evidence-reports-and-saved-result-boundaries), [ADR-0010](../docs/architecture/ADR-0010-package-manager-semantic-facts-and-runtime-dependency-state-composition.md) for operation semantics, and [ADR-0013](../docs/architecture/ADR-0013-versioned-native-reconstruction-and-workspace-checkpoint-storage.md) for storage. This plan coordinates a trial within those meanings.

| Approach | What it earns | Decision |

Keep command provenance in existing facts and source references. A first-view headline or separate source viewer adds presentation scope without evidence it is needed. |
| Record the version loaded by pytest | Answers a stronger question about the actual process. Requires a target-owned observation and separate qualification. | Leave to the runtime evidence owner. It is independent of conveying the source declaration. |

Use existing report schema and shared CI projection. Example proposed workflow detail for Backend verification.

> Static pip request in `signatures`: HTTPX 0.27.0. This matches the old version in the PR. The command text records the requested version. Installed and tested versions remain unverified by this fact.

Report the request next to the exact workflow source and the relevant job and step locator. Any recorded job outcome remains a separate fact. Preserve a neutral rendering for requests that match the proposal or another version. No default success, inferred mismatch, package-state outcome or maintainer action follows from the presence or absence of the declaration.

## Admission and ownership

- Begin with an admitted exact dependency transition and an exact-head readable workflow definition. The shell owner provides analyzable command occurrences with source positions. Admit a sole ordinary top-level command in an analyzed run step for the first increment. Preserve its static scope even if a corresponding job or step is skipped.
- Reuse the dependency-owned `PackageManagerOperationDeclaration` for supported `pip install` forms. Reuse one operation declaration per occurrence for this interpretation and the existing direct requirements analysis. Determine argument roles from the admitted atoms without splitting raw command text or using a text search as evidence. Keep any broader runtime semantic resolution outside this slice.
- The request must be a positional, literal named requirement for the changed package with one concrete `==` operand. Reuse the existing requirement/normalization tools. Admit valid named extras with the same exact pin and handle a recognized literal `-r` or `--requirement` operand separately. A token that looks like a pin when used as an option operand is still an option operand. Begin with the observed literal forms and reject unclear argument grammar rather than guessing what an option consumes. Preserve the requested token and version spelling. Relate it to the old/proposed versions using the established package/version normalization convention, with no solver inference.
- Suppress the first-slice declaration for dynamic or unsupported command/operand structure, unclassified options, URL/marker/range/wildcard forms for the selected package, and multiple conflicting pins within one command. Treat those as outside the supported declaration surface. Distinct commands and jobs keep distinct source scope. If multiple commands request different versions, show their individual declarations without choosing an effective final version. A workflow with no admitted declaration retains its existing view.
- The dependency owner determines argument meaning. CI binds the normalized package, requested version and literal token to repository/revision, workflow path, job, step source index and the existing command occurrence location. Reuse the run/workflow and dependency input context for inherited identity. No separate shell parser, generic command catalog, or expanded acquisition is needed.

## Persistence and report integration

Keep the new fact alongside workflow CI coverage details without changing the coverage state, reason, consumption, invocation, or runtime proof. Extend the native coverage representation through an explicit coverage codec version 2 with a historical version-1 decode path. Other family versions and Workspace storage schema keep their existing contracts. Do not add fields to the fixed version-1 layout or infer that old captures evaluated this capability. Historical absence is distinct from an evaluated result with no supported request. Use the existing Workspace publication path and native basis links. Recovery validates supported layout, package and revision/job/step membership against the saved CI input, and verifies the saved command span against the retained run text. The existing parser supplies command spans, so the first citation points to the command rather than claiming a parser-provided token span. Recovery reads the recorded argument interpretation without rerunning shell analysis or package semantics. If compatible decoding cannot be implemented within this boundary, return to design before expanding the storage change.

Project the new record into existing workflow-scoped report facts with exact evidence linkage through the shared full/partial mapping. Preserve existing report and Workspace recovery behavior for historical inputs. The new result must be readable in the normal report and after reopening the saved report. Open a wider inspection surface only if this delivery demonstrably leaves the source recovery task unmet.

## Build sequence and proof

1. Prove the smallest parser-to-fact slice on both OmniMatch commands and the observed `-r` combination. Contrast with the existing changed-requirements install from pedido-service. Add targeted controls for exact proposed/other versions, option-value lookalikes, dynamic and non-exact input, repeated/conflicting pins and a skipped or conditional context. Confirm an unrelated dependency remains outside the changed-package projection.
2. Carry the fact through the normal investigation and shared CI preparation, native capture and cold recovery. Prove old checkpoint/report compatibility, source binding, version refusal and corruption controls. Preserve native coverage and runtime-state outcomes on equivalent inputs. Use retained or controlled external inputs first. Keep the real public baseline and any control inputs clearly distinguished.
3. Compare the recovered maintainer detail with the saved OmniMatch baseline and closest controls. A development pass requires the two exact workflow reasons to be visible, the same proof limits to be understandable, references to be inspectable, and unrelated reports to stay quiet. Focused checks precede broader validation. Use existing workflow/command/storage bounds. A new live capture is only justified by a distinct remaining proof obligation and a separately scoped budget.

Stop the trial if ordinary source inspection meets the same maintainer task with comparable effort, source binding cannot remain exact, compatibility requires unrelated migration, or the new text suggests effective runtime behavior beyond the evidence. Independent usefulness, pytest verification of the proposed version, and automated check/merge authority are separate responsibilities.
