# End-to-End Product Flow Learning and Evidence-to-Action Execution Plan

**Status:** admitted bounded execution/learning plan; live step selection remains owned only by `../MEMORY.md`  
**Responsibility:** turn the current-system audit into a Learning-by-Doing product progression from verified end-to-end flow ownership, through correction of admitted baseline defects, to one evidence-backed non-abstention maintainer-action path when and only when its normal producer prerequisites are proven  
**Parent execution owner:** [Overall Evidence Sufficiency and Maintainer Action Synthesis Plan](OVERALL_EVIDENCE_SUFFICIENCY_AND_MAINTAINER_ACTION_SYNTHESIS_PLAN.md)  
**Primary audit input:** [AUDIT-008 — Current System End-to-End Evidence-to-Action Audit](../audits/2026-09-19_AUDIT-008_current-system-evidence-to-action-readiness.md)  
**Stable semantics:** [Product Decision Model](../docs/specifications/UPGRADEPILOT_PRODUCT_DECISION_MODEL_SPECIFICATION.md), [Maintainer Action Synthesis](../docs/specifications/UPGRADEPILOT_MAINTAINER_ACTION_SYNTHESIS_SPECIFICATION.md), [Core Pipeline and Contract](../docs/specifications/UPGRADEPILOT_CORE_PIPELINE_AND_CONTRACT_SPECIFICATION.md)  
**Method:** canonical A → B → C → D → E Learning-by-Doing, composed with Planning/Design, Build/Implement, Audit/Review, testing, and working-memory procedures as each slice requires

## 1. Purpose

UpgradePilot now has enough implemented foundation and audit evidence that continuing as isolated local fixes would create avoidable drift.

This plan coordinates one coherent journey:

```text
understand the actual current product flow
→ own the important evidence/proof boundaries
→ repair already-admitted correctness/trust problems
→ compare action-relative missing premises
→ select one decision-critical producer/composition responsibility
→ build and prove that responsibility
→ admit one maintainer-action path only when positive permission is earned
→ integrate that action into product presentation
→ prove one credible bounded public-PR synthesis flow
```

The plan deliberately combines **learning ownership** and **product implementation**. Learning is not a detached course before engineering, and implementation is not allowed to outrun understanding of the evidence/decision boundary being changed.

This plan is subordinate to the parent synthesis plan. It does not redefine accepted action semantics, product scope, architecture, or live state.

## 2. Completion outcome

The responsibility is complete only when the selected journey has produced all of the following:

1. Ali can trace the current normal product path at an engineering-ownership level:
   ```text
   public PR
   → exact identity / dependency transition
   → evidence producers
   → technical applicability/investigation
   → PublicPullRequestInvestigation
   → maintainer-action synthesis
   → product presentation
   ```
   including where evidence is static, runtime-correlated, inferred, unresolved, or unavailable.

2. Interactive Learning-by-Doing has established ownership of the verified current flow and evidence boundaries. A durable learning artifact is **optional and created only when Ali explicitly requests one**; it is not a completion gate for this plan.

3. Already-admitted baseline behavior is trustworthy enough for stronger synthesis work:
   - material branch-stopping uncertainty is not silently lost by the abstention evaluator;
   - public acquisition authentication behavior is deliberate enough for the proof being run;
   - current audit/live-state coordination does not point normal continuation at a stale workstream.

4. The project has compared the remaining action-critical producer/composition gaps against **specific positive action permissions**, rather than implementing F4/F5/F6/F7 as a backlog.

5. One selected evidence producer/composition responsibility is implemented and proven end-to-end through its normal application path.

6. At least one non-abstention action is admitted only if its exact positive prerequisites and close defeaters are proven through normal producers. If no action can yet earn permission, honest abstention remains the valid result and the plan stops at the exact missing premise.

7. Human-facing and, when justified by the selected product boundary, machine-readable presentation consumes the admitted synthesis result without overstating evidence.

8. A representative public-PR proof demonstrates the strongest result actually earned at that point, with exact revision/provenance and explicit claim limits.

## 3. Learning goals and depth

### Ownership depth — must become durable

Ali should be able to independently reason about:

- the end-to-end producer → composition → consumer flow;
- the difference between **observation**, **interpreted evidence**, **technical proposition/applicability**, and **maintainer-action permission**;
- exact identity/provenance and why revision/job/source relationships cannot be guessed;
- why conservative `unresolved`/unsupported states are often correct behavior rather than defects;
- how to locate the **earliest sufficient owner** of a proposition before adding downstream checks or metadata;
- why passing tests prove bounded behavior but do not establish product necessity or stronger evidence;
- how positive permission and defeaters are tested for one maintainer action;
- how a real product gap is distinguished from missing breadth, missing proof, and stale coordination.

### Working depth — learn when the selected responsibility reaches it

Reach implementation-level working understanding for:

- `PublicPullRequestInvestigation` composition;
- `maintainer_action.py` synthesis and residual uncertainty;
- relevant CI/Target/impact producers selected by the action proof;
- public authentication/transport configuration when F9 is handled;
- focused tests and application integration tests for the selected path;
- any exact target/runtime witness selected later.

### Lookup/deferred depth

Do not require memorization of:

- every GitHub/PyPI API field;
- every parser grammar node;
- all wheel-tag rules before a wheel-tag producer is selected;
- every product-simulation scenario;
- all shell/matrix/reusable-workflow forms;
- agent/framework internals not required by the selected product responsibility.

These remain lookup-level until real work makes them material.

## 4. Learning-by-Doing execution contract

Every substantive slice follows the canonical cycle proportionately.

### A — orientation before action

Before changing or deeply evaluating an unfamiliar responsibility:

- teach what the slice owns;
- place it in the actual product flow;
- identify the exact input/output/evidence type;
- explain what would and would not be proven by success;
- identify one or two professional engineering ownership skills naturally exercised;
- state what depth is required now and what remains deferred.

Do not ask Ali to reason from premises that have not been explained or recently reconstructed.

### B — real bounded action

Perform the actual selected operation:

- source/test trace;
- design comparison;
- implementation;
- regression test;
- runtime proof;
- audit/review;

but keep one semantic responsibility per slice.

### C — progressive preservation

At meaningful checkpoints:

- update the active working-memory record;
- update `MEMORY.md` only when live selection/milestone/blocker changes;
- update the plan only when execution coordination itself changes;
- preserve proof debt explicitly;
- promote stable semantics/methods only to their real specification/ADR owners.

### D — ownership check from the real work

After evidence exists:

- explain the actual source/control/data/evidence flow;
- compare planned vs observed behavior;
- inspect proof and non-proof;
- ask a small number of meaningful reasoning questions;
- prefer prediction, diagnosis, trace, critique, or changed-case reasoning over recall quizzes.

### E — gap repair and next-slice orientation

Use Ali's answers and the observed evidence to:

- repair only important misunderstandings;
- distinguish project gap from learning gap;
- explain why the next slice follows;
- stop rather than continue when the next responsibility has not earned selection.

The cycle is not a ceremony gate. If a concept is already owned, compress A/D/E. If a slice exposes a new proof model or architecture boundary, deepen them.

### Slice-closure and deferred-proof rule

For every substantive slice, normally complete **A → B → C → D → E before silently selecting the next substantive responsibility**.

The primary operation and the LbD cycle remain distinct:

```text
primary operation
→ owns the detailed procedure and authorization boundary

A → B → C → D → E
→ owns the project-level working/learning rhythm around that operation
```

A Build implementation may therefore have source/test edits completed in B while executable proof is temporarily unavailable. In that case:

1. C records the exact proof debt and does not call it a pass;
2. D teaches/reviews what was actually implemented and source-reviewed;
3. E repairs ownership gaps and orients the deferred proof responsibility;
4. the later executable validation is treated as its **own bounded evidence slice** with a fresh proportional A → B → C → D → E cycle;
5. the parent engineering responsibility remains **not technically closed** until its required executable proof passes.

Do not keep B conceptually half-open while waiting for an unavailable runtime path, and do not skip D/E merely because tests are deferred. Conversely, completing D/E does not upgrade deferred validation into proof.

`MEMORY.md` alone states which phase/slice is live.

## 5. Execution sequence

### Product-flow reconstruction and ownership baseline

**Responsibility:** reconstruct one accurate current end-to-end product model before changing the action layer.

Trace the current normal path from real source/tests:

```text
CLI/input
→ PR identity + changed/exact files
→ dependency change + source contexts
→ CI run/job/workflow evidence
→ static consumption + runtime strengthening
→ PyPI release evidence
→ upstream repository / release interval / semantic support-drop evidence
→ target relevance
→ mechanism-specific impact/applicability
→ artifact target evidence boundary
→ PublicPullRequestInvestigation
→ standalone synthesis evaluator
→ current evidence-report CLI
```

For each material handoff record:

- producer;
- exact evidence/proposition produced;
- provenance/identity carried;
- consumer;
- unsupported/unresolved/failure state;
- proof limit;
- whether the relation is normal-path reachable.

Use representative source/tests and real preserved cases only when they discriminate the flow. Do not read every file merely for completeness.

**Learning output:** interactive source-backed explanation, reasoning checks, and working-memory preservation are sufficient for this main workstream. Create a durable learning/reference artifact only when Ali explicitly requests one; learning-artifact authoring is not an automatic step or gate here.

**Proof/pass condition:** Ali can trace a representative dependency update through the major handoffs and explain at least one point where stronger evidence is unavailable without conflating that with a negative compatibility conclusion.

**Stop line:** no product source mutation in this slice. If reconstruction exposes a new correctness defect more fundamental than AUDIT-008-F3, reconcile the audit/plan before building.

### Honest abstention synthesis baseline — AUDIT-008-F3

**Responsibility:** make the already-admitted abstention evaluator preserve material branch-stopping uncertainty sufficiently to explain why stronger actions are unavailable.

Start from normal-shaped investigation states where technical branches stop before final impact evaluation, including representative:

- upstream/source acquisition or authority problems;
- package/release problems when action-relevant;
- Target environment problems;
- support-drop semantic problems;
- conditional investigation state where material.

First determine the **smallest synthesis-owned projection** of those states. Do not duplicate entire domain result objects or create a generic evidence graph.

Compare any real design alternatives only on:

- semantic correctness;
- earliest owner of the uncertainty;
- whether synthesis must explain it;
- duplication risk;
- extensibility only for already-admitted result classes;
- testability.

**Build proof must include:**

```text
branch-stopping material problem
→ visible in abstention explanation/residual uncertainty

same investigation with non-material adjacent state
→ no noisy generic dump

supported/closed path
→ no manufactured uncertainty

multiple material problems
→ deterministic, bounded preservation

all non-abstention permissions still unavailable
→ action remains abstain
```

Include focused evaluator tests and at least one normal-shaped application/investigation fixture boundary. Use broader regression only after focused proof passes.

**Implementation/proof staging:** the Build implementation slice and executable validation may be separate A → B → C → D → E slices when execution is temporarily unavailable.

- **Implementation slice:** orient the synthesis responsibility, implement the bounded projection/tests, preserve exact source-review/proof debt, complete ownership check, and orient validation.
- **Executable validation slice:** when an execution path is available, orient the proof claims, run focused evaluator tests, the normal-shaped investigation integration proof, then the appropriate broader deterministic regression; preserve exact outputs, interpret proof/non-proof, and repair/close accordingly.
- F3 is **not technically complete** merely because implementation and test code exist. It closes only when the required executable proof passes.

**Learning ownership target:** Ali should be able to explain why this is a synthesis correctness repair rather than a new evidence producer or new action permission, and why source-reviewed test code is not the same thing as executed proof.

**Stop line:** do not add non-abstention actions, CLI recommendation rendering, generic result registries, or new evidence acquisition in this slice. Do not advance to F9 as though F3 has closed while its required executable proof remains debt.

### Public acquisition trust boundary — AUDIT-008-F9

**Responsibility:** make public GitHub authentication behavior deliberate enough that an unrelated ambient credential cannot silently change the proof being performed.

Before design, distinguish:

```text
public anonymous acquisition
authenticated public acquisition
rate-limit / authorization requirement
ambient shell state
proxy/transport state
```

Compare the smallest credible configuration mechanisms. The design must preserve legitimate authenticated use without exposing secret values.

**Proof must include:**

- anonymous public path does not silently inherit unrelated credential state under the selected contract;
- explicit authenticated path still works at the adapter/configuration boundary;
- secret values are never printed/persisted;
- authentication failure remains distinct from source absence and transport failure;
- CLI/help/documentation contract, if changed, remains clear.

**Learning ownership target:** Ali should be able to explain configuration-as-input versus ambient environment state and why this matters to reproducible evidence acquisition.

**Stop line:** do not redesign all networking/proxy handling or create a credential manager unless separately justified.

**Responsibility:** determine which exact missing premise should become the next product capability after the admitted baseline is trustworthy.

For each action still under consideration, trace:

```text
accepted permission
→ exact premises
→ currently reachable producers
→ composition
→ missing/weak premise
→ closest defeater
→ product value if repaired
```

Use the accepted synthesis specification rather than re-defining action meanings.

Candidate gaps from AUDIT-008 include:

**Learning ownership target:** Ali should be able to defend why the selected producer/composition gap matters to an action and why the rejected candidates are deferred rather than forgotten.

**Stop line:** select **one** next responsibility. Do not convert the comparison into a multi-gap roadmap.

### Selected evidence producer/composition build

This slice is parameterized by the action-relative selection above. It is intentionally not pre-designed here.

For the selected responsibility:

1. identify the exact proposition;
2. identify the earliest sufficient producer/owner;
3. define the minimum trusted result type/state only if current types are insufficient;
4. connect the normal producer → application composition → consumer path;
5. preserve explicit unavailable/unsupported/ambiguous states;
6. implement focused positive, negative, identity-mismatch, and close-defeater tests;
7. prove normal-path integration;
8. run the appropriate broader deterministic regression;
9. obtain hosted/live proof only when the claim requires it.

**Examples of entry-specific guardrails:**

- **F4:** preserve exact workflow/revision/source/job relation; do not infer runtime execution or exact wheel compatibility.
- **F5:** exact target-supported wheel tags require target-owned evidence; do not derive them from UpgradePilot's own runtime or broad runner/Python labels.
- **F6:** collect only the runtime version/artifact facts required by the selected proposition; no generic log-ingestion subsystem by default.
- **F7:** define a bounded positive coverage horizon; do not claim universal risk discovery.

**Learning ownership target:** Ali must be able to trace the new evidence from origin to action-relevant consumer and state what it still does not prove.

Potential surfaces:

### First credible bounded public-PR synthesis proof

**Responsibility:** evaluate the integrated path against a representative real public dependency-update PR without mutating the target repository.

Proof record should freeze:

- UpgradePilot revision;
- target repository/PR/base/head identity;
- public acquisition/authentication mode;
- local semantic deployment identity if invoked;
- evidence producers actually activated;
- resulting action/abstention;
- residual uncertainty;
- exact claim limits.

A real run may still correctly produce `abstain`. The proof succeeds when the system behaves consistently with the evidence and accepted permission semantics—not when it produces a more active action.

**Stop line:** no target mutation, automatic merge/close, unsafe third-party execution, or post-hoc weakening of evidence standards to obtain a preferred result.

## 6. Proof ladder

Use the smallest proof level that establishes the current claim:

```text
source reasoning
→ focused unit/contract tests
→ application composition/integration tests
→ full deterministic product regression
→ fresh installed-package/hosted proof
→ live public-provider proof
→ live local-model proof
→ representative public-PR synthesis proof
```

Do not require every level for every slice.

Conversely:

- unit tests do not prove live provider/model behavior;
- hosted deterministic tests do not prove a target's exact runtime environment;
- one real public case does not prove broad product coverage;
- a passing action fixture does not prove the action is normally reachable.

## 7. Working-memory and learning-artifact discipline

Maintain the selected active working-memory record throughout substantive execution. Record:

- A/B/C/D/E state for each meaningful slice;
- source-backed discoveries;
- design decisions and rejected alternatives;
- test/runtime evidence;
- user reasoning/ownership checks;
- proof limits;
- changed route and exact stopping point.

Do not use working memory as a tutorial.

If Ali explicitly requests a durable flow learning artifact, route it through the normal learning-artifact procedure and keep it non-controlling. Otherwise, preserve reusable engineering progression in conversation plus working memory only; do not create learning-note artifacts automatically.

## 8. Prohibited scope

This plan does not authorize or require:

- re-planning the whole UpgradePilot project;
- reopening closed Cycle-1/2/3 command-analysis work without regression evidence;
- implementing all AUDIT-008 findings;
- generic planner/rule-engine/evidence-graph infrastructure;
- broad agentic orchestration;
- framework adoption because it is educational;
- universal GitHub Actions/shell/matrix/reusable-workflow support;
- generic job-log or artifact ingestion before a proposition requires it;
- deriving exact target compatibility from broad static labels;
- weakening provenance or conservative unresolved states for product coverage;
- adding all maintainer actions at once;
- new product-simulation cases without a named surviving evidence question;
- target repository mutation or automatic merge/close behavior.

## 9. Plan change triggers

Revisit this plan only when:

- AUDIT-008 is materially superseded by new evidence;
- accepted action semantics change in their specification;
- a selected producer responsibility reveals an architecture decision too consequential for this plan and requires an ADR;
- a supposedly local repair changes the end-to-end responsibility boundary;
- real proof falsifies the assumed dependency order;
- the user deliberately changes the learning/building operating rhythm.

Ordinary implementation detail, one test result, or one completed A→E slice belongs in working memory and `MEMORY.md`, not as churn in this plan.

## 10. Handoff rule

At every stopping point answer four questions:

```text
What product responsibility is now established?
What can Ali now explain/diagnose at ownership depth?
What proof exists, and what does it not prove?
What exact proposition/responsibility is selected next?
```

If the fourth answer is not evidence-backed, stop and decide before building.
