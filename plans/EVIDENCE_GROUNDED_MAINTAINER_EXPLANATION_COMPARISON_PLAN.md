## Maintainer task and baseline

Given a real dependency update and its admitted source findings, can a maintainer correctly explain what was established, which applicability premise remains unresolved, and which feasible observation would resolve it? Compare the strongest transparent presentation that uses the existing product projections with one structured LLM explanation on the same frozen evidence. The [90-day plan](UPGRADEPILOT_90_DAY_PLAN.md#evidence-grounded-ai-design-checkpoint) owns the wider AI sequence. Use the [feasibility plan](PRODUCT_VALUE_AND_TRANSPARENT_BASELINE_FEASIBILITY_INVESTIGATION_PLAN.md) for baseline and consumer selection and the [usefulness plan](MAINTAINER_REPORT_PRESERVATION_AND_USEFULNESS_EVALUATION_PLAN.md#5-independent-usefulness-evaluation) for independent benefit.

Start with a read-only baseline walkthrough on the exposed HTTPX PR. Use the saved report, selected source spans and native premises from the [connected qualification](../working-memory/evidence/2026-11-07-native-proxy-successor/RESULTS.md). Capture the current answer and identify a concrete obstacle to completing the task, such as locating the decisive premise or connecting it to a feasible test observation. Consider a concise deterministic arrangement of the same fields as the comparator if layout alone can remove the obstacle. Freeze that comparator before viewing model output. If the transparent route already meets the task, choose a different demonstrated explanation gap through the same review or defer the comparison.

For HTTPX, the example expected answer describes the conditional five-keyword fit under the sampled Starlette HTTPX fallback, the unknown installed binding and branch, and a scoped observation at the `TestClient` call that could resolve that branch. Any separately retained CI context must carry its own capture identity and observation scope. The November source-only invocation leaves CI/runtime unperformed. The historical Docker build and October empty query remain separate evidence. [Applicability disposition](../working-memory/2026-11-07_httpx-ci-runtime-applicability_cycle.md)

## Comparison contract

1. Freeze a development packet from the exposed HTTPX case and, if available, one contrast case chosen for a materially different source or missing-evidence outcome. Record the eligible pool, rejections, prior exposure, target/source identities and case roles before reviewing candidate outputs. Known cases support development. Reserve unseen eligible material for any later transfer claim and treat repair-driving cases as development evidence for the changed method.
2. Build the packet from fixed native records and exact retained excerpts. Both treatments receive the same information, source locators, versions, roles, omissions and separately scoped observations. Freeze the deterministic presentation, task, rubric and expected propositions before inference. Keep answer keys and forbidden-claim labels out of the packet. Carry enough supporting material to judge citations. Fail packet admission when a necessary premise cannot be retained or fitted.
3. Use one direct, local model configuration as the initial candidate. Structure its proposed explanation as supported observations with reference IDs, unresolved premises, and evidence needed to resolve them. Validate schema, reference membership and exact target/revision association in code. Review whether each citation actually supports its claim, whether a material premise was omitted, and whether the proposed check would resolve the stated gap. Treat output as experimental explanation under the [Product Decision Model](../docs/specifications/UPGRADEPILOT_PRODUCT_DECISION_MODEL_SPECIFICATION.md) and [action synthesis](../docs/specifications/UPGRADEPILOT_MAINTAINER_ACTION_SYNTHESIS_SPECIFICATION.md).
4. A later execution contract binds model, backend, rendered input, prompt/schema, sampling settings, cases, fixture identities, input/output limits, request count, deadlines, local retention ceiling and cleanup. Proposed development ceiling is one mechanical canary and up to two case predictions, one attempt per role, with up to 8,192 rendered input and 1,024 generated tokens per call. Propose up to 300 seconds per prediction and 960 seconds for the batch including bounded finalization. Confirm fit, a qualified clock and the actual host envelope before activation. Use the applicable [run-control requirements](INVESTIGATOR_RUN_CONTROL_COMPLETION_AND_CAPABILITY_DIAGNOSTIC_PLAN.md). An admission or canary failure withholds subsequent calls. Stop after a decision-critical unsupported claim, invalid boundary or exhausted budget according to the frozen adjudication protocol. Any successor uses a new freeze, with no automatic retries or ceiling enlargement.
5. Keep a local run receipt with exact evidence and configuration identities, offered and cited reference IDs, validation/review results, elapsed time, usage or explicit unknown usage, and cleanup. Retain original output and failures with private data under [Security](../SECURITY.md). Treat PR prose, code and logs as untrusted input. The first comparison has no provider acquisition, target execution, write tools or external telemetry. Compare fixed material using an experiment-local entry point if implementation is later selected, with dependencies governed by the [experiment boundary](../experiments/README.md).

An adequate candidate preserves every decision-critical fact and condition, avoids unsupported runtime or action claims and provides a specific source-supported answer. Benefit requires a recorded improvement on the baseline task, such as a justified next check the baseline omits or fewer source opens to reach the same correct answer in a comparable task. Source-open counts are a proxy. Human time and usefulness require separate measurement. A setup or control failure is inconclusive for semantics. A faithful answer without added value favors the transparent baseline. A promising development result is eligible for separate frozen transfer evaluation and independent usefulness review.

## Multi-agent evidence investigation

**Learning milestone.** Build and diagnose a separately selected, offline comparison on a saved dependency update with two useful questions that can be investigated independently. The fixed-evidence explanation comparison comes first in the product sequence. An isolated exercise can use injected workers or approved retained material to learn coordination and failure handling before product eligibility. It yields learning evidence and a measured trade-off. The [project checkpoint](UPGRADEPILOT_90_DAY_PLAN.md#evidence-grounded-ai-design-checkpoint) governs product entry after interpretation qualification and a demonstrated tool-selection need.

- **Source worker.** Use bounded read-only source tools to identify the affected call, the old and proposed signatures and any unresolved binding premises.
- **CI worker.** Use bounded read-only CI evidence tools to distinguish configured tests, observed execution and what the available run can establish about the affected path.
- **Coordinator.** Assign the two questions, receive structured findings and expose disagreements or missing results. Each worker chooses its own next permitted read or stops within its allocation. Each result carries the target identity, exact source or record references, supported observations, unresolved premises and stop reason. Keep saved observations attached to their original captures. Validate references and target/revision joins in existing deterministic owners. The coordinator's output stays a proposal under the existing synthesis rules.

Compare one tool-using agent with the two workers and coordinator on the same task, model configuration, evidence eligibility and total budget. Count coordination and finalization in the shared ceiling for calls, read operations, tokens and elapsed time. Reserve enough budget to return a useful partial result when a worker stops. Freeze the case selection, expected evidence, tool permissions, resource allocations and stop rules before a selected run. Start with ordinary Python as the control and use the same worker contracts if a LangGraph implementation is selected. Keep framework effects separate from the effect of splitting the task. If a result could be explained by extra model calls or fixed task decomposition alone, use a fixed split as a follow-up comparator before attributing the gain to autonomous delegation.

Measure required evidence found, unsupported claims, preserved unknowns, stopping quality, latency and usage. Exercise a worker timeout, a wrong-revision citation and a legitimate empty result. A timed-out worker stays incomplete and its peer's valid results remain available. A wrong-revision citation is refused. An empty result stays scoped to the worker's available evidence. Preserve the trace and inspect where the failure or disagreement entered. Learning succeeds when Ali can diagnose one failure from that trace and explain whether delegation helped. Product pilot eligibility requires an improvement on a real maintainer task within the frozen budget and authority limits, followed by the applicable transfer and usefulness gates.

## Review and handoff

Accept or narrow the design after checking the task, comparator and criteria. The subsequent readiness review decides whether to freeze a runnable comparison or defer with the observed reason. Inference, experiments, dependency additions, native integration and separate learning-branch work require their own selected scope. A model comparison cannot resolve missing target observations or grant maintainer action authority.
