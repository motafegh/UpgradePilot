# 1. What does “CI dependency exercise” mean?

## CI

**CI** means **Continuous Integration**.

Practically, it refers to automated workflows that run when code changes—for example:

```text
install dependencies
run tests
run linting
build the package
```

In UpgradePilot’s current scenario, those workflows belong to the public pull request being investigated.

## Dependency exercise

“Dependency exercise” does **not** merely mean:

```text
The CI workflow was green.
```

It means something narrower:

```text
The workflow consumed the changed dependency
and exercised the changed package.
```

For the current supported rule:

```text
consumed the dependency
=
installed the explicitly identified requirements file

exercised the package
=
directly invoked the changed package
```

For example:

```bash
pip install -r requirements-dev.txt
pytest tests
```

Here:

* `requirements-dev.txt` is consumed through `pip install -r`;
* `pytest` is directly invoked;
* therefore, under the current admitted rule, CI exercised the changed `pytest` dependency.

The module explicitly says it answers only this narrow question. It does **not** establish full test coverage, compatibility, safety, or a maintainer decision.

# 2. The exact Step 7 product question

We can express the evaluator’s question as:

> Does at least one successful CI path, tied to the pull request’s exact current revision, provide admitted evidence that it installed the changed dependency source and directly exercised the changed package?

Break that into five requirements:

```text
1. The CI job completed successfully.
2. The workflow run completed successfully.
3. The workflow definition belongs to the exact PR head revision.
4. The workflow visibly installs the explicitly supplied requirements path.
5. The workflow directly invokes the changed package.
```

All five are required for the current `proven` result.

# 3. What does “exact-head” mean?

A Git commit is identified by a **SHA**, commonly pronounced “shah.”

**SHA** originally refers to **Secure Hash Algorithm**, although in Git discussions it usually means the commit’s hash identifier.

A pull request has a **head commit**: the latest commit containing the proposed changes.

Suppose the PR head is:

```text
f3cda8a94600e58d27f1bc17c99b7693718b6350
```

UpgradePilot must make sure that:

```text
workflow run head SHA
=
workflow job head SHA
=
workflow-definition revision
=
pull-request head SHA
```

Why?

Because this would be unreliable:

```text
CI result from commit A
+
workflow definition downloaded from later commit B
```

The downloaded workflow might have changed after the CI run. UpgradePilot would then be interpreting the wrong instructions.

So **exact-head evidence** means that the evidence is anchored to the precise revision being evaluated.

We are only introducing this concept now. We will inspect its acquisition and validation mechanisms when the Step 7 trace reaches those modules.

# 4. The three states

The source defines this type:

```python
type DependencyCIExerciseState = Literal[
    "proven",
    "no_successful_ci",
    "unresolved",
]
```

A `Literal` type tells the type checker that the value must be one of those exact strings.

## `proven`

Meaning:

```text
At least one successful exact-head CI path satisfies
the currently admitted dependency-consumption and
package-exercise rule.
```

It does **not** mean:

```text
the update is safe
the update is compatible
all tests passed everywhere
the maintainer should merge
the dependency has no vulnerabilities
```

It proves only the narrow CI dependency-exercise claim.

## `no_successful_ci`

Meaning:

```text
No completed successful exact-head job is available.
```

Examples:

* there were no workflow inputs;
* all available jobs failed;
* jobs were cancelled;
* jobs did not complete successfully.

This state concerns the **absence of successful execution evidence**.

## `unresolved`

Meaning:

```text
Successful exact-head CI exists,
but the admitted rule cannot prove dependency exercise.
```

Examples:

* CI passed, but the workflow definition cannot be retrieved;
* the retrieved workflow definition belongs to another revision;
* CI ran `tox`, but UpgradePilot does not yet trace the `tox` configuration;
* the requirements path was not independently established;
* the installation and package invocation occur in a structure the current command reader does not support.

This state concerns **interpretation or proof insufficiency**, not execution absence.

The evaluator’s three exact meanings are documented in both the function and its controlled tests.

# 5. The most important distinction

This is the conceptual center of Step 7:

```text
No successful CI occurred
≠
Successful CI occurred, but dependency exercise was not proved
```

Therefore:

```text
no successful job
→ no_successful_ci

successful job, insufficient proof
→ unresolved
```

Why does this distinction matter?

Suppose a workflow passes but runs:

```bash
pip install tox
tox -e py
```

The package may have been tested indirectly through `tox`. But the current evaluator does not trace `tox.ini`, `pyproject.toml`, or the virtual environment that `tox` creates.

It would be incorrect to say:

```text
no_successful_ci
```

Successful CI did exist.

It would also be incorrect to say:

```text
proven
```

The current admitted evidence rule did not establish the dependency path.

The honest result is:

```text
unresolved
```

The repository includes this exact negative test.

# 6. What enters the evaluator?

The public function is conceptually:

```python
evaluate_dependency_ci_exercise(
    dependency,
    workflow_inputs,
    *,
    direct_requirements_install_path,
)
```

It receives three categories of information.

## A. Canonical dependency identity

```python
dependency: DependencyVersionChange
```

For the controlled test:

```text
package: pytest
normalized package: pytest
old version: 9.0.2
proposed version: 9.0.3
```

“Canonical” means this has already become the trusted common representation used by downstream modules, regardless of which supported dependency-file format originally produced it.

We will trace `DependencyVersionChange` backward later. For now, its practical responsibility is:

> Tell Step 7 exactly which package and version transition is being evaluated.

## B. Workflow evidence bundles

```python
workflow_inputs: Sequence[WorkflowDependencyExerciseInput]
```

Each input contains:

```python
run
jobs
definition
```

That means:

```text
run
→ summary of the workflow execution

jobs
→ individual execution records within that run

definition
→ exact workflow YAML content, or explicit evidence that it was unavailable
```

It is called a **bundle** because these pieces belong to one workflow execution and must be interpreted together.

## C. Explicit installation path

```python
direct_requirements_install_path: str | None
```

For the proving test:

```text
requirements-dev.txt
```

The `*` before this parameter makes it **keyword-only**.

So the caller must write:

```python
direct_requirements_install_path="requirements-dev.txt"
```

rather than passing an unexplained positional string.

That is useful because this value carries important semantic responsibility.

# 7. Why is the requirements path supplied separately?

This is a major architecture point.

A dependency may have source evidence such as:

```text
requirements-dev.txt
uv.lock
constraints/base.txt
```

That evidence establishes something like:

> This file contributed evidence that the dependency changed.

It does **not automatically establish**:

> This exact file was installed by CI using a currently supported operational rule.

Those are different claims.

Consider `uv.lock`.

A lock file may prove that a package version changed. But this command:

```bash
pip install -r uv.lock
```

is not automatically a valid or admitted installation interpretation merely because `uv.lock` appeared in the dependency evidence.

Similarly, a constraints file can constrain versions without itself being the primary installed requirements source.

Therefore, Step 7 deliberately refuses to convert generic dependency evidence paths into installation proof. The caller must provide a separately established, source-specific operational path. The tests explicitly protect `uv.lock` and `constraints/base.txt` from accidental promotion into proof.

The mental model is:

```text
Dependency-file evidence:
“This file helped establish the version change.”

Operational CI evidence:
“This explicitly established requirements path was installed by CI.”
```

Related, but not interchangeable.

# 9. Per-workflow result versus overall result

These are not the same object.

## Per-workflow result

```python
WorkflowDependencyExerciseResult
```

Answers:

> What did this specific workflow prove?

It includes:

```text
workflow name
workflow path
state
reason
detail
matched installation command
matched execution command
```

## Overall result

```python
DependencyCIExerciseResult
```

Answers:

> Considering every available workflow, what is the overall CI dependency-exercise state?

It includes:

```text
overall state
overall reason
overall detail
all per-workflow results
```

The aggregation rule is existential:

```text
Does any admitted workflow prove dependency exercise?
```

So:

```text
one proven workflow
+
one failed or unresolved workflow
→ overall proven
```

But the weaker workflow is not deleted or hidden. Its result remains available for transparency.
