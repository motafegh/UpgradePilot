# 10 — Product Simulation Ownership Workbook

**Purpose:** Convert exposure into demonstrable understanding through explanation, tracing, diagnosis, prediction, and bounded execution.  
**Current status:** Exercises available; completion and capability evidence must be recorded separately.  
**Rule:** Do not mark a task complete because an answer was read or approved.

## 1. How to use this workbook

Each task has four possible depth states:

- **Not attempted** — no evidence.
- **Guided** — completed with direct AI steps or answer structure.
- **Assisted** — completed with source access and limited prompts.
- **Independent at stated scope** — completed without substantive answer generation, then reviewed against evidence.

Record:

- date;
- exact task;
- sources allowed;
- assistance received;
- answer or artifact produced;
- errors and corrections;
- demonstrated depth;
- what remains unproven.

Approval of an AI answer is not independent completion.

## 2. Foundation checks

### Task 2.1 — Explain the interruption

Without opening the parent plan, explain:

- the implementation failure pattern;
- why manual simulation was selected;
- why complete product behavior and artifact behavior must be investigated together;
- why M2-S03 remains paused.

**Pass evidence:** Accurate explanation with no claim that the old implementation was rejected.

### Task 2.2 — Authority map

Draw the local authority order from external constraints through active scenario evidence.

Then answer:

- what local simulation rules may override;
- what they may never override;
- what Ali's current explicit instruction changes.

### Task 2.3 — Non-admission examples

For five methods used or considered in simulation, classify:

- manually useful;
- stable candidate;
- admission status;
- implementation status;
- proof limits.

Include at least one connector, script, model, container, and human-review example.

## 3. Runtime and artifact-model checks

→ raw/reference evidence

### Task 3.2 — Artifact responsibility test

For every default artifact, answer:

1. What question does it own?
2. What information must not be placed there?
3. What would be lost if it were removed?
4. Which S001 or S002 example demonstrates the need?
5. Is the logical responsibility stable, conditional, or unresolved?

### Task 3.3 — Representation separation

Use one S002 finding and represent it as:

- raw capture;
- evidence item;
- interpretation;
- finding;
- decision reason;
- machine-report projection;
- human-report sentence.

Do not copy existing text. Preserve authority differences.

### Task 3.4 — Run-boundary prediction

For each change, decide whether to update the same record, create a new decision version, create a new run, or create a comparison:

- head SHA changes;
- only human-report wording changes;
- new exact-head pytest result arrives;
- upstream changelog typo is corrected;
- resolver output changes materially;
- Ali accepts the case conclusion;
- previous finding is contradicted.

Explain each choice.

## 4. Evidence and lineage checks

### Task 4.1 — Backward trace

Choose one material sentence from either human report and trace it through:

```text
report
→ decision reason
→ finding or limitation
→ claim or interpretation
→ evidence item
→ operation
→ raw/reference source
→ frozen identity
```

Record exact IDs and paths.

### Task 4.2 — Evidence-state classification

Classify and explain:

- API returned no records because the connector did not expose a push-triggered workflow;
- historical job log returns HTTP 410;
- a file does not apply to the selected ecosystem;
- two tagged sources disagree;
- a raw payload was observed but not preserved;
- a previous date statement was corrected;
- a JSON file fails schema parsing;
- a current URL points to a changed branch rather than the frozen revision.

Use distinct states where justified.

### Task 4.3 — Authority matrix

Build an authority matrix for:

- PR metadata;
- lockfile;
- manifest;
- tagged source;
- changelog;
- package registry;
- advisory;
- workflow definition;
- CI run;
- CI log;
- maintainer comment;
- model interpretation.

For each, state:

- strongest supported question;
- one unsupported question;
- required corroboration or target join.

### Task 4.4 — Bounded absence claim

Take three statements that use words such as `none`, `never`, `not used`, or `not present`.

Rewrite each to include:

- revision;
- searched path or method;
- observation boundary;
- dynamic or hidden-path limitation;
- permitted conclusion.

### Task 7.5 — Thesis matrix

## 8. S003 preparation checks

### Task 8.1 — Candidate screening rubric

Convert the S003 mandatory and rejection criteria into a bounded review form.

Do not turn every possible source into a mandatory checkbox. Preserve the purpose of each criterion.

### Task 8.2 — Candidate review

For one real public candidate, record only screening evidence:

- exact locator;
- dependency transition;
- failing check accessibility;
- causal ambiguity;
- comparison boundary;
- safety and scope;
- accept/reject decision;
- reason.

Do not create the selected run unless all criteria pass and selection is authorized.

### Task 8.3 — Initial checkpoint construction

For a selected hypothetical case, create draft content for:

- invocation;
- frozen identity;
- initial manifest;
- first operation event;
- initial ownership state;
- baseline input snapshot.

Prohibited: adding a cause, repository-specific finding, or final decision before evidence acquisition.

### Task 8.4 — Hypothesis table

Create candidate causes:

- update-caused;
- pre-existing;
- flaky;
- environmental;
- unrelated;
- mixed;
- unresolved.

For each, record:

- supporting evidence expected;
- contradicting evidence expected;
- best comparison;
- failure signature;
- decision effect;
- next action.

### Task 8.5 — Comparability audit

Compare two executions and explicitly list:

- same revision or not;
- same command or not;
- same workflow version or not;
- same runner/platform/toolchain or not;
- same dependency resolution or not;
- same external service conditions or not;
- same failure signature or not;
- permitted causal conclusion.

### Task 8.6 — Two-axis decision test

Construct a scenario where:

- dependency evidence supports acceptance;
- a pre-existing CI failure blocks the PR.

Write a one-axis decision and show its ambiguity. Then write a two-dimension representation without claiming it is the final schema.

### Task 8.7 — Stop decision

Given incomplete comparison evidence, decide whether to:

- continue;
- switch method;
- stop resolved;
- stop unresolved;
- reject the candidate.

Justify through expected decision value, cost, authorization, and comparability.

## 9. Validation and review checks

### Task 9.1 — Validator audit

Inspect a validation result and answer:

- what method ran;
- whether the method is preserved;
- what bundle state it validated;
- which checks were performed;
- whether current inventory still matches;
- what proof limits are stated;
- whether the result is reproducible.

### Task 9.2 — Deliberate defect injection

On a temporary local copy, introduce one defect at a time:

- broken JSON;
- duplicate ID;
- missing evidence reference;
- wrong run ID;
- missing raw path;
- report/decision mismatch;
- hidden superseded record.

Run or design validation and explain the expected diagnostic.

Do not modify accepted repository evidence for this exercise.

### Task 9.3 — Review-state separation

For S001 or S002, write separate current statements for:

- execution;
- factual review;
- Ali review;
- external confirmation;
- AI assistance;
- Ali independent capability.

No statement may imply another.

## 10. Capstone ownership assessment

Complete one bounded case segment with reduced AI assistance.

Possible scopes:

- candidate screening;
- exact identity freeze;
- dependency-role mapping;
- CI-authority audit;
- baseline execution;
- backward lineage trace;
- structural validation review;
- causal hypothesis comparison.

Required evidence:

1. task boundary selected before execution;
2. source and method choice justified;
3. exact work performed by Ali recorded;
4. AI assistance recorded precisely;
5. result and limitations explained by Ali;
6. one challenge or correction handled;
7. reviewer assesses the stated scope only;
8. no general capability claim beyond demonstrated evidence.

## 11. Suggested assessment rubric

| Dimension | Weak evidence | Operational evidence | Ownership-practice evidence |
|---|---|---|---|
| Mental model | repeats labels | explains relationships | predicts and corrects new cases |
| Source use | accepts summary | locates exact source | chooses and bounds sources |
| Lineage | names artifacts | traces references | diagnoses broken lineage |
| Uncertainty | says “not sure” | identifies missing evidence | selects proportionate next evidence |
| Decision | repeats outcome | explains stronger/weaker limits | constructs and challenges a bounded action |
| History | reads final state | explains supersession | preserves progressive state honestly |
| Assistance | omitted | declared generally | exact contribution and dependence recorded |

## 13. Package completion boundary

The learning package is not complete until at least:

- one accurate full-runtime explanation;
- one exact backward lineage trace;
- one S001 correction analysis;
- one S002 CI-authority analysis;
- one cross-case classification exercise;
- one S003 candidate or checkpoint exercise;
- one validator review;
- one bounded capstone performed with recorded assistance.

Even then, completion establishes only the scopes actually demonstrated.
