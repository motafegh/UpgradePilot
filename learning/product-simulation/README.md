# Product Simulation Learning Package

**Status:** Current learning entry point for the separately governed `product-simulation/` domain.  
**Purpose:** Build accurate understanding and ownership of the complete manual runtime, artifact lifecycle, evidence reasoning, baseline comparison, and prospective S003 process.  
**Current demonstrated depth:** AI-produced learning package grounded in two completed retrospective cases; Ali review and independent ownership exercises remain required.

## Why this package exists

`product-simulation/` is not an extension of M2-S03 implementation work. It is the current product-discovery domain used to manually perform the intended UpgradePilot runtime before more implementation resumes.

The learning responsibility is therefore broader than reading a plan or memorizing artifact names. The learner must understand:

- why implementation was interrupted;
- how a real dependency-update event becomes a bounded maintainer decision;
- why narrative, runtime state, evidence, interpretation, findings, decision, reports, follow-up, and review are separate responsibilities;
- how missing, expired, contradictory, superseded, and inaccessible evidence changes the result;
- how a transparent baseline tests the project thesis;
- how retrospective reconstruction differs from prospective execution;
- which observations are repeated candidates, conditional responsibilities, contradicted assumptions, or unresolved;
- why simulation usefulness does not admit a permanent architecture or prove automated capability;
- what Ali must independently explain, challenge, trace, and perform before ownership can be claimed.

## Depth scale used in this package

- **Introduced:** terminology and purpose can be recognized.
- **Operational understanding:** the learner can explain the flow and predict common outcomes with the sources open.
- **Implementation-adjacent understanding:** the learner can inspect artifacts, trace references, diagnose representation or validation defects, and propose bounded corrections.
- **Ownership practice:** the learner can perform a scoped task, justify method choice, preserve evidence, challenge conclusions, and explain limits with reduced AI assistance.
- **Independently owned:** requires demonstrated performance outside this package; it is not granted by reading or approving notes.

Most lessons target operational or implementation-adjacent understanding. The workbook contains ownership-practice tasks. S003 is intended to provide the first prospective execution evidence.

## Learning method

For each lesson:

```text
predict
→ inspect the named project source
→ explain the mechanism in your own words
→ trace one real S001 or S002 example
→ diagnose one failure or limitation
→ answer the ownership checkpoint
```

Do not read all source artifacts passively. Use exact IDs, revisions, artifact paths, and state transitions.

## Core mental model

The complete simulated runtime is approximately:

```text
real dependency-update event
→ invocation
→ discovered and frozen case identity
→ material operations
→ raw or referenced source material
→ evidence items and evidence states
→ attributed claims and interpretations
→ repository-specific findings
→ transparent baseline result
→ bounded decision
→ machine and human reports
→ user action and follow-up state
→ rerun, replay, or supersession
→ factual review, Ali review, external confirmation, and ownership assessment
```

This is an open-world model. A case may add, split, reorder, repeat, or stop responsibilities when evidence requires it.

## Package boundaries

This package does not establish:

- a final production schema;
- accepted persistence architecture;
- a service or agent design;
- universal reliability from two cases;
- correctness or safety of the target updates;
- that S001 or S002 was executed prospectively;
- that Ali independently owns the concepts;
- that M2-S03 implementation may resume.

9. explain the S003 causal-attribution design;
10. perform selected workbook tasks with declining AI assistance.
