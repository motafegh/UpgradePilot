# AUDIT-014 — Product value and evaluation sequencing

**Audit date:** 2026-10-20  
**Branch:** `audit/project-wide-system-audit-2026-10-20`  
**Main revision last reconciled:** `a1c291c6cf9238493eeb666b184192ed178b90f1`  
**Mode:** cross-responsibility Repository Audit  
**Authority:** non-controlling audit evidence. This record does not authorize benchmark execution, model calls, product Build, target execution or external acquisition.

## 1. Audit question

For the current UpgradePilot implementation and retained development evidence:

> What would actually demonstrate that UpgradePilot adds useful maintainer information beyond `simulation-transparent-baseline-v0.1`, and which next engineering/evaluation investment is justified before more expensive semantic/agent work?

This audit examines the Charter thesis, transparent comparator, current product output boundary, S001–S016 development evidence, the prepared product-value feasibility plan, its October 20 review amendment, and retained Investigator experiment evidence/cost.

## 2. Executive assessment

The recent **product-value-first direction is correct and should be preserved**. UpgradePilot should not respond to repeated Investigator semantic failures by automatically adding prompts, models, agents, roles, framework machinery or another large qualification matrix.

The prepared feasibility plan is structurally strong but **not ready to execute in its branch-point form**. Four review amendments already requested on October 20 are materially justified, and this audit adds one further requirement: evaluation mode/proof class must remain explicit so historical simulation output, current-source projection, deterministic component proof, retained replay and fresh end-to-end product output are never pooled as if they were equivalent product runs.

The strongest immediate conclusion is therefore:

```text
preserve product-value feasibility gate
→ amend its case-screening and semantic-adequacy rules
→ make proof/evaluation mode explicit
→ deep-inspect only the smallest discriminating cohort
→ select the cheapest owner that can change maintainer value
→ run another semantic/multi-role/model experiment only if a residual semantic question remains after that trace
```

There is no evidence in this audit that the accepted hybrid Evidence → Interpretation → Validation → Decision architecture should be replaced.

## 3. What the product is actually trying to beat

The controlling transparent baseline is intentionally restricted to four input families:

- version-change category;
- current CI conclusion;
- dependency directness;
- literal release-note keyword signals.

It deliberately cannot inspect workflow/job relevance, environment identity, dependency paths, selected extras/groups, functional usage, sentence semantics, target relevance or source authority. Its comparison dimensions already include action, reasoning, uncertainty, targeted action, evidence authority, failure behavior, cost and user value.

That is a sound comparator for the Charter thesis. The mistake would be to reduce the comparison to one categorical action-match score.

### Current action asymmetry

Current product synthesis admits only:

```text
MaintainerAction = Literal["abstain"]
```

and deliberately withholds merge, targeted-check, investigate, block and defer until their positive permissions are proven through normal product producers.

The transparent baseline can emit more active coarse outcomes. Therefore a present-day product-versus-baseline evaluation has **two different responsibilities**:

1. **information value:** does richer evidence remove unsupported reassurance, add a supported material finding, localize uncertainty, identify a more discriminating next check, or correctly stop unnecessary investigation?
2. **action permission:** has the product separately earned a stronger maintainer action?

The first can improve while the second remains `abstain`. Conversely, blanket abstention is not automatically useful merely because it avoids false positives.

A fair evaluation must report both. It must not score the current product as action-superior simply for abstaining, nor score it as useless solely because the positive action layer is intentionally not yet admitted.

The screen found:

Therefore missing baseline/current-product artifacts in later cases are readiness findings, not permission to fabricate a benchmark denominator or silently derive human conclusions into the product arm.

## 5. Findings

### AUDIT-014-F1 — P1: case selection must be responsibility-driven, not chronology-driven

**Finding:** confirmed plan-design weakness in the branch-point feasibility plan.

The original S001–S006 inventory reflects historical programme chronology. It omits later distinct product responsibilities that can materially change the next investment decision.

**Required correction:** incorporate the October 20 two-level design:

```text
S001–S016 light screen
→ classify eligibility, distinct responsibility, retained evidence, evaluation mode and exposure
→ select smallest discriminating deep cohort
→ perform detailed readiness/consumer trace only there
```

Keep the same six-active-engineering-hour ceiling. Do not require a fixed deep-case count.

### AUDIT-014-F2 — P1: evaluation mode/proof class must be first-class

**Finding:** additional plan clarification required.

The repository currently contains several materially different evidence forms:

```text
historical manual/AI-assisted simulation
current-source projection
retained deterministic component evidence
controlled offline replay with frozen intermediate
fresh current end-to-end product output
```

They answer different questions. A historical `BASELINE_RESULT.json` may compare the baseline with the historical simulation’s full investigation; it does not prove what the current product produces. A source projection such as S015/S016 can identify current behavior/limitations but is not a product execution.

**Required correction:** every deep-cohort row and any later comparison protocol must name the exact mode for each arm, revision/input identity, manual preparation/injected premises and the claim that mode can support.

Do not call an altered no-model route the unchanged fresh product when normal product execution conditionally invokes the local semantic extractor.

### AUDIT-014-F3 — P1: information value and action permission must be evaluated separately

**Finding:** confirmed evaluation-interpretation requirement.

Because current synthesis admits only `abstain`, direct categorical action comparison alone is structurally confounded by product maturity.

The comparison must separately evaluate:

- supported material findings/reasons;
- unsupported reasons removed;
- uncertainty location/narrowing;
- source/evidence authority correction;
- discriminating next evidence/check;
- correct stopping/pruning;
- operational/failure behavior;
- cost;
- final action permission.

A useful report finding can be real product value before positive action permission exists. It must be labelled as such rather than promoted into action superiority.

### AUDIT-014-F4 — P2: all S001–S016 remain exposed development material

**Finding:** confirmed proof-boundary requirement.

The scenarios have been used for design, simulation, debugging, planning or recent Investigator work. S006 additionally records oracle/exposure limitations. Later cases do not become protected holdouts merely because a specific recent model batch did not use them.

**Consequence:** a future claim that a materially tuned semantic method/general product method transfers beyond development cases requires a separately frozen method and newly protected material. Development/source-aware review remains useful for diagnosis and local correctness.

### AUDIT-014-F5 — P1: another semantic/model experiment is not yet the default next investment

**Finding:** confirmed strategic sequencing constraint.

AUDIT-011 found that the recorded Investigator lineage spent approximately 91.1% of attempts on qualification while complete semantic outputs still contained navigation, entailment, calibration and completion failures. Later supplied-evidence r4/r5 diagnostics completed their bounded cohorts but still produced semantically inadequate results across the four exposed cases, despite some accurate partial corrections.

At the same time, S007–S016 expose several precise deterministic/state/provenance/applicability responsibilities. Some are current implementation boundaries, not missing general language understanding.

**Decision rule:** choose another semantic experiment only when the selected producer→consumer trace shows that:

1. the necessary facts/relations are actually available at the correct owner;
2. deterministic/native repair cannot answer the material gap cheaply enough;
3. the unresolved question is genuinely interpretation/validation rather than acquisition, binding, applicability, projection or action-permission logic;
4. the experiment can discriminate the proposed semantic mechanism from a simpler alternative.

### AUDIT-014-F6 — P2: bounded multi-role decomposition is a valid candidate, not an architecture decision

**Finding:** October 20 patch B is justified at the option-selection level.

The evidence does not support “more agents are smarter.” Earlier Fixed work already had multiple stages and still failed. Additional roles also add cost and handoff failure modes.

However, a later **same-evidence, responsibility-isolated** experiment could be discriminating if current deep tracing shows that facts are present but one-pass interpretation repeatedly conflates relation building, proposition assessment, uncertainty handling and reporting.

If selected later, the hypothesis should test responsibility decomposition/scoped contexts/typed handoffs, preferably without immediately confounding it with different model families or an agent framework.

### AUDIT-014-F7 — P2: semantic adequacy must be premise-based, not citation-cardinality-based

**Finding:** October 20 patch C is required.

A citation list can be non-empty while failing to entail a material claim. Conversely, a bounded abstention or request for missing evidence may be correct when it explicitly preserves an unresolved premise rather than inventing a negative fact.

Future evaluation should ask whether every material premise is supported, contradicted, overstated or unresolved and whether decision-critical unknowns remain visible.

### AUDIT-014-F8 — P2: findings/action contracts must not self-authorize execution

**Finding:** October 20 patch D is required.

A complete findings packet may remove the need for another redundant plan document, but it does not itself authorize Build, benchmark execution, inference, acquisition, target execution or action admission. Explicit review/selection is still required, with `MEMORY.md` owning the live continuation.

### AUDIT-014-F9 — RETAIN: six-hour zero-execution feasibility gate remains proportionate

**Finding:** justified complexity / cleared concern.

The six-active-engineering-hour total with zero model calls/GPU/network/target/benchmark execution remains a good constraint **if** the S001–S016 pass is genuinely lightweight and deep work is restricted to a discriminating cohort.

Expanding the case screen should reallocate the first readiness block, not expand total time.

## 6. Recommended next decision structure

The feasibility investigation should compare only evidence-backed candidate increments exposed by the deep trace:

1. reuse/repair an existing deterministic producer or projection;
2. bounded deterministic source-fact/relation derivation;
3. finite current-product versus transparent-baseline comparison where exact modes are ready;
4. positive action-permission/synthesis work where existing producer facts can meet an accepted permission;
5. single-pass semantic diagnostic where a residual interpretation question remains;
6. bounded multi-role interpretation/validation experiment where responsibility isolation is the discriminating hypothesis;
7. materially different deployment/model experiment only for a named deployment-quality residual;
8. narrow/defer/stop.

Do not rank options by novelty. Rank them by expected decision information, maintainer benefit, reachability, proof strength, engineering/operating cost, and what they allow the project to stop doing.

## 7. Likely discriminating cohort roles, not frozen cases

Before deep inspection there should be no fixed case count. The screen suggests these roles are useful if their exact modes remain supportable:

- a **baseline-sufficient/no-added-value control** — S004 is a strong candidate;
- a **coarse-baseline false-reassurance/miscalibration case** — S002 or S005;
- a **supported upstream/target-applicability information case** — S001;
- a **current deterministic transfer/boundary case** — S015 or S016;
- optionally one materially different artifact/environment/history case such as S008/S011/S012 if a current reachable consumer exists without manual oracle injection.

This is screening guidance, not cohort selection.

## 8. What should be changed now

Before executing the prepared feasibility investigation:

1. revise `plans/PRODUCT_VALUE_AND_TRANSPARENT_BASELINE_FEASIBILITY_INVESTIGATION_PLAN.md` to incorporate October 20 patches A–D;
2. add the explicit evaluation-mode/proof-class distinction from F2;
3. make information-value versus action-permission scoring explicit from F3;
4. preserve the six-hour/zero-execution ceiling;
5. leave historical simulation/experiment outputs unchanged;
6. use this Stage-2 record, rather than rewriting historical planning evidence, to explain why the plan changed on the audit branch.

## 9. Stop line

Do not run the feasibility investigation, benchmark arms or another semantic/model experiment merely because this audit identified a better protocol.

First revise and verify the owning plan. After that, the audit/correction programme can either continue to Stage 3 or explicitly select the bounded feasibility investigation when its information value is worth the time.
