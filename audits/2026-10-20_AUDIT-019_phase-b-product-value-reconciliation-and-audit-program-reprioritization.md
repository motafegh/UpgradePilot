## 3. Why S002/S004 are a credible next comparison

### S004 — calibration/value control

S004 contains a retained normal-product CI/native path where the current native result preserves:

- supported static dependency declarations;
- successful retained CI observations;
- `supported_not_correlated` CI coverage rather than promoted execution certainty;
- unresolved manager-environment evidence in runtime package-state assessment.

The current native owner therefore already expresses a narrower and better-calibrated boundary than a coarse "passing CI" input can express.

The historical transparent baseline for S004 selected `merge_after_normal_review` from patch-size + passing CI + known directness + no caution keyword, while explicitly admitting it could not determine changed-version installation/exercise. This makes S004 a legitimate **baseline-sufficient/no-added-value control candidate**, not a guaranteed UpgradePilot win.

The comparison should test whether the native facts materially improve uncertainty/evidence authority/actionability, not merely whether they are more detailed.

### S002 — missing-evidence/uncertainty control

The October retained capture has no returned CI runs. The comparison must preserve that exact horizon and may not borrow the historical July passing-Docker observation.

This is useful because the baseline should already be cautious under missing/unknown CI. The native side must therefore demonstrate actual incremental value in localized uncertainty/evidence authority, or honestly show no material benefit.

"Zero returned runs in this capture" must not become "CI never existed."

## 4. Accepted comparison boundary

The proposed comparison is acceptable **only as a component information-value comparison**, not as a full UpgradePilot-versus-baseline benchmark.

The two arms are asymmetric:

```text
transparent baseline
→ four restricted inputs
→ coarse maintainer action + reasons/limits

retained native-CI component
→ exact retained Workspace/native CI families
→ scoped facts / uncertainty / evidence authority
→ no full-product action available in this experiment
```

Therefore:

- do not score action superiority;
- do not claim an abstain/native side "wins" merely by being conservative;
- compare supported reasons, localized uncertainty, evidence authority, justified next-evidence questions, failure behavior and cost;
- keep the full-product/action dimension explicitly unavailable for the component arm.

This asymmetry is a limitation, but not a fatal flaw, because the selected question is deliberately narrower than the Charter's complete product thesis.

## 5. Required negative-result scope

Before execution, preserve this interpretation rule explicitly:

> **A negative result means only that the retained native-CI component showed no material incremental information value over transparent baseline v0.1 on the two exposed S002/S004 cases under the frozen October evidence boundary.**

It does **not** establish that:

- UpgradePilot as a whole has no product value;
- deterministic/native evidence is generally unhelpful;
- other evidence families have no value;
- the hybrid architecture is wrong;
- Workspace migration should be abandoned;
- another case/mechanism would produce the same result;
- no future full-product or independent-maintainer evaluation is worthwhile.

Likewise, a positive result establishes only a narrow exposed-case component benefit. It does not prove general reliability, action superiority, maintainer usefulness or architecture adoption.

This scope should appear in the execution/result packet, not merely in this audit.
