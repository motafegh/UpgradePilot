## 2. Design correction that governs this research

Main is **not** trying to make UpgradePilot or its LLM responsibility permanently minimal.

The intended engineering rule is:

```text
DO NOT optimize for minimum mechanism count.

DO optimize for:
real product capability
+ useful reasoning depth
+ clear authority ownership
+ evidence-backed complexity
+ meaningful learning/engineering exposure.
```

Complexity is welcome when it buys something real, for example:

- broader supported investigation situations;
- better prioritization of evidence;
- adaptive sequencing;
- cross-responsibility reasoning;
- stronger observability/replay;
- better failure handling;
- meaningful AI/LLM engineering learning;
- a capability that would otherwise become brittle or combinatorial in deterministic orchestration.

Complexity is unwanted when it is primarily:

- redundant model echo of trusted data;
- speculative framework/infrastructure;
- ceremony that does not change a decision;
- a fabricated action/case added only to make the planner look more agentic;
- a large abstraction around a responsibility that a small deterministic rule already owns better.

Therefore the current first-seam contract should be understood as **evidence-refined**, not as the desired upper bound of planner capability.

## 3. Core research question

Find real evidence for the following question:

> Where in realistic dependency-update investigations can a bounded LLM planner/controller add material value over fixed/mechanism-specific deterministic sequencing, while deterministic code continues to own source identity, action authority, execution, evidence interpretation/promotion, proof strength, and final trusted state?

A candidate is especially valuable when the reasoning problem involves some combination of:

```text
several propositions / evidence gaps
+ several genuinely useful read-only investigations
+ prerequisite/dependent relationships
+ action history or failed attempts
+ competing information value / cost
+ different supported responsibility boundaries
+ a bounded step budget
+ an important stop/defer/unresolved choice
```

The goal is **not** to maximize the number of tools. The goal is to discover where model-driven planning becomes materially more useful than a few obvious conditionals.

## 4. Research priorities

### Priority A — discover independently justified planner-visible capabilities

Look for recurring investigation responsibilities that could plausibly become bounded, read-only capabilities.

Do not assume the current `acquire_exact_target_python_declaration` action is the final shape or the only useful family.

Potential inspiration from prior simulation work includes, but is not limited to:

- targeted behavioral/reproduction checks;
- exact-head environment or dependency-resolution evidence;
- mediated CI/runner consumption proof;
- artifact history/provenance acquisition;
- repository-purpose/provenance context acquisition;
- upstream mechanism/candidate discovery;
- exact source/configuration acquisition that resolves a cross-domain applicability gap.

These are **research prompts, not pre-approved actions**. Reject them if the evidence does not justify planner exposure.

For every candidate capability, answer:

1. What exact planning uncertainty does it discriminate?
2. What exact evidence would it acquire or produce?
3. What inputs/locators can remain deterministically pre-bound?
4. Is it read-only and safely bounded?
5. What existing UpgradePilot owner already covers part/all of it?
6. Is it recurring/general enough to deserve a capability, or is it one-off case logic?
7. Would a small deterministic rule select it just as well in all relevant states?
8. What becomes difficult/brittle/combinatorial if fixed orchestration owns the selection policy?
9. What new AI/LLM engineering concept or learning value would this capability genuinely expose?
10. What is the strongest claim this capability may establish, and what remains outside its authority?

### Priority B — find real planning situations with meaningful choice

Prefer real cases where the planner would have to reason rather than merely repeat an obvious one-action rule.

Useful shapes include:

```text
A. two or more independently justified actions are available
→ which one has the highest discriminating value now?

B. one action is useful only after another proposition is established
→ sequence/prerequisite reasoning

C. several propositions are unresolved but only one matters to the bounded question
→ relevance/prioritization

D. a useful next responsibility is identifiable but unsupported
→ defer rather than fabricate a tool

E. adjacent/deeper uncertainty remains but the owned question is settled
→ stop rather than continue because something is unresolved

F. previous action failed or became stale
→ choose another useful path, stop, or defer rather than blindly repeat
```

## 5. What not to manufacture

Do not:

- invent a second planner action merely because multi-action planning sounds more impressive;
- wrap an already-obvious deterministic step in an LLM-facing tool without showing planning value;
- choose a case only because it produces the desired `choose_action`, `stop`, `defer`, or `unresolved` label;
- convert product-simulation artifacts into product schemas;
- use simulation findings as automatic architecture authority;
- assume a complex planner is valuable merely because it is complex;
- assume a small first-seam contract means the eventual planner should remain small;
- design the fresh v3 protocol before the capability/case research tells us what claim is honest.

A valid research conclusion may be:

```text
no second independently justified action/capability found yet
```

That is preferable to manufacturing one.
