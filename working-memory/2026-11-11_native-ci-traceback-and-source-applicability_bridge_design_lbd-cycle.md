## External feasibility: supported API but uneven available access

- Official GitHub REST job-log and step-log docs: `https://docs.github.com/en/rest/actions/workflow-jobs`. A job-log or individual step-log endpoint returns a short-lived redirect to text; docs describe anonymous public access subject to actual access. The log redirect expires after approximately 1 minute. October 2026 GitHub retention changes mean logs/runs/statuses share an Actions retention setting (default 90 days; public configurable 1–90), so absence/expiry is expected: `https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository`.
- Real case: connected GitHub tool successfully read backend job `125180284415` for PR #11 / run `41416124208` attempt 1. The same job log records successful installation of FastAPI 0.104.1, Starlette 0.27.0, HTTPX 0.28.1 and a pytest collection `TypeError: Client.__init__() got an unexpected keyword argument 'app'`. This is **externally acquired evidence**, not a native UpgradePilot result.
- Two limited **unauthenticated** public API probes to exact job `125180284415` from the authorized environment returned **HTTP 403**, with *no redirect* and no response body read: `GET /actions/jobs/{id}/steps/5/logs` and `GET /actions/jobs/{id}/logs`. The source of refusal (permissions, throttling, transport, API behavior) was not disambiguated. It disproves a guarantee of successful current *anonymous* access from this environment; it does **not** prove all public log access is impossible. Do not silently use `GITHUB_TOKEN` or assume connected plugin credentials exist in the product.

## The decision: justify a narrower **on-demand native CI failure diagnostic**

**User problem:** On a Python dependency-update PR with a concrete conditional source incompatibility, what error (if any) did the corresponding exact GitHub Actions test actually produce, under what installed state and what remains unproven? An install-success summary, an observed pytest traceback, and a source-level mismatch can reinforce one another, but the report must keep their separate timing, provenance and authority.

**Recommended design over alternatives:**
- **Preferred:** optional bounded CI-failure evidence acquisition selected for an *already identified task-relevant failed job/step* after complete run/attempt/head/job validation; retain a narrow, typed observation and expose it in a **new** combined/opt-in investigation revision. Keep source-only default exactly as is and do not run on every CI job.
- **Too narrow to count as end-to-end product value:** download raw logs and print them without a typed interpretation and traceable report/source reference; or attach external connector output to an old report without recording its acquisition method/scope.
- **Too broad:** monitor every failed job, automatically feed arbitrary logs to an LLM, capture all artifact/trace formats, run target workflows or infer fixes/merge permission.
- **Cheaper no-Build comparator:** let a human or assistant inspect exact GitHub job logs outside the product as we did. This already answers this AV-Tracer question, so product implementation must earn its *repeatable, provenance-preserving delivery* value on a second contrasting case and a missing/blocked control.

## Candidate implementation contract to review before activation

1. **Eligibility and frozen identity:** start from native exact repository/PR/base/head/dependency identity; identify eligible failed job/step in an attempt-bound run. Join `(repository, head_sha, run_id, run_attempt, job_id, step_number)`; verify the job belongs to that run and expected head in the attempt-specific API. Do not infer execution from the static YAML if current correlation says unresolved. Budget candidate count to avoid downloading unrelated E2E or frontend failures.
2. **Provider transport:** add an owner-scoped method to `github/actions.py` or its existing HTTP layer for **at most selected exact step logs** when supported (with a bounded job-log fallback, not automatic). Follow only validated GitHub-provided temporary redirects under an explicit allowlist/redirect policy. Enforce physical-request, redirect-hop, timeout, byte and decoded-text budgets before allocation and decompression. Preserve HTTP 403/404/expired/too-large/malformed/partial states without retries or credential escalation. A 403 in this environment blocks claiming default anonymous qualification.
3. **Source/observation extraction:** create a CI-owned typed observed error/evidence result with the *minimum* relevant retained lines and offsets, raw-content digest and immutable source locator; preserve what was actually observed at `Run pytest` and any installation observation from the same job with separately named step/timing. Treat textual phrases as potentially untrusted and context-dependent; errors that do not match an admitted shape remain `unclassified`, not `safe`. No target execution or model verdict.
4. **Conditional composition:** retain source-level `unexpected_keyword: app` and observed `Client.__init__` rejection as **separate evidence** unless provenance/source paths and actual exercised chain legitimately connect them. Same-process `httpx.__version__` / module-file identity still remains unobserved without a target-owned instrumented trace. If CI step log comes from another run/head/attempt/environment or the branch isn't established, do not join. No inference that the upgrade alone caused the entire multi-job run to fail or that a fix is automatically authorized.
5. **Native delivery:** use one selected Workspace/native capture/reconstruction and report path (new view revision or explicitly enabled composite mode), with method, content/retention scope, source links, gap states and original text/decoded limits. A new combined result may say “observed matching pytest exception” but cannot **retroactively mutate** the already saved source-only report, or silently convert its `not_evaluated` states into `evaluated`. Retention must be designed for sensitive logs: avoid uploading raw third-party logs to the public repository; digest-only with no retained excerpt cannot promise offline reinspection.
6. **End-to-end verification:** controlled clean, conflicting, missing, truncated, timeout/403/404/expired, wrong-head/attempt/job/step, wrong relative step, alternative traceback, unchanged source-only/normal defaults, exact package and error wording, masked/unsupported CI correlation, privilege/redirect/secret guard, report/open-source/cold-Workspace recovery. Qualify with exact live AV-Tracer job if obtainable through the **product transport**, plus a genuinely contrasting failed/negative case and an inaccessible-log case. Record actual request/byte limits and refusal; do not count connector success as normal-product proof.
7. **Scope/security gate:** log confidentiality, bounded storage/retention and a single shared source-plus-CI physical acquisition budget must be resolved **before** combining previously separate invocation profiles. Current caller-signature acquisition had consumed 51/56 GitHub requests in the known AV-Tracer run, so simply reusing its remaining allowance is not a responsible combined acquisition budget. No default token inheritance or target process execution.

**Conditional stop criteria:** If bounded anonymous log access cannot be established and explicit `token-env` capability is not acceptable for this product slice, defer the product log feature or define a truthful authenticated-only supported mode; do not simulate a successful anonymous live qualification. If the product cannot compose the needed source/runtime claims without disproportionate schema/orchestration change, first implement the smallest end-to-end CI observation consumer that earns a separate maintainer task, and defer the combined profile with explicit reason.
