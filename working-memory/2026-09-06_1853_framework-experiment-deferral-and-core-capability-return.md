# Framework Experiment Deferral and Core Capability Return

**Date/time:** 2026-09-06 18:53 +03:30  
**Session status:** ACTIVE  
**Primary responsibility/mode:** Planning/Design + Learning-by-Doing route reconciliation

## 1. Decision point

The ordinary-Python bounded planner control and the bounded LangGraph implementation now have enough executable evidence to judge the current one-action orchestration seam. The real pydantic Python-support flow is green, controlled semantic comparison is green, and LangGraph value/cost findings are recorded.

The next question was whether to proceed immediately into a LangChain executable integration experiment.

Inspection of the current product and reasoning owners changed that route.

## 2. Current product pressure

UpgradePilot already has many deterministic evidence-acquisition and interpretation responsibilities in the normal public pull-request investigation path, including dependency identity, CI evidence, package/release evidence, upstream repository/release/changelog evidence, Python-support interpretation, target relevance, and candidate applicability.

However, the currently admitted planner-selectable investigation surface is still only one action:

```text
acquire_exact_target_python_declaration
```

The Python-support selector therefore currently presents a very small real orchestration problem:

```text
one admitted useful read
or
explicit no-action / rejection / failure
```

This is sufficient to learn and prove bounded planner/authority/orchestration mechanics, but it is not yet sufficient product pressure for a meaningful higher-level agent loop or multi-tool orchestration evaluation.

The accepted planner plan already defines the richer-planning reactivation pressure as multiple independently admitted capabilities plus real states where relative value/order depends on proposition state, prerequisites, consumed history, failures, or budget and a small fixed policy becomes materially brittle or contextual.

## 3. Why executable LangChain integration is deferred

LangChain can be useful for a single agent, model abstraction, tool calling, agent loops, middleware, and lifecycle behavior. The deferral is not a claim that LangChain requires multiple agents.

The current reason is narrower:

```text
higher-level agent framework machinery
+
one genuinely planner-selectable product action
→ weak discriminating evidence about framework value
```

Building a LangChain tool loop now would risk manufacturing framework usage rather than solving a product responsibility. It could also blur the already-proven boundary:

```text
model proposal
!= deterministic execution authority
```

Therefore the current framework work should close with a proportionate LangChain relevance checkpoint, not an executable LangChain integration.

## 4. Core capability pressure already waiting

The existing product has a more important unfinished responsibility: the materially different artifact-serviceability / installation-mode mechanism.

Current source already contains:

- artifact-serviceability candidate and applicability logic from old/proposed release artifact inventories;
- target-side artifact-environment interpretation from exact workflow definitions;
- explicit proof-strength separation between static configuration and runtime execution.

But those capabilities are not yet fully connected through the normal `PublicPullRequestInvestigation` application path.

Completing this second mechanism through the real application path is more valuable now because it creates genuine heterogeneous reasoning pressure rather than framework-shaped pressure.

## 5. Formal continuation sequence

### Step 1 — LangChain relevance checkpoint

Learn/confirm only the minimum LangChain concepts needed to make the current deferral decision well-founded:

```text
single-agent agent loop
model abstraction
tools / tool calling
middleware / lifecycle hooks
relationship to LangGraph
```

Output: a concise finding explaining which abstractions could become useful later, which do not solve a current product problem, and what trust/authority risks must remain explicit.

No LangChain dependency or experiment code is justified at this step.

### Step 2 — close the current framework experiment package

Record a bounded disposition covering:

```text
ordinary-Python control
→ retained as a simple proven reference/control asset

LangGraph
→ retained as a proven viable orchestration experiment with explicit topology/observability value and real ceremony cost

LangChain
→ conceptually relevant but executable integration deferred for insufficient current action-space pressure
```

Do not claim adoption, rejection, product integration, or general framework superiority.

Close/update the relevant framework working-memory handoff so future continuation starts from the re-entry trigger rather than assuming LangChain implementation is immediately next.

### Step 3 — return to the core impact/applicability/investigation responsibility

Re-anchor on the accepted **Impact, Applicability, and Investigation Foundation Plan** and current implementation owners.

Before new product implementation:

1. reconcile any active plan/file identity that still uses obsolete coordinate-heavy naming;
2. establish exactly where artifact-serviceability and target artifact-environment work stopped;
3. inspect the normal `PublicPullRequestInvestigation` composition gap;
4. define the smallest coherent continuation/proof slice.

### Step 4 — connect the second materially different mechanism through the real application path

Continue artifact-serviceability / installation-mode reasoning using real admitted evidence and target applicability without duplicating product/domain truth.

The goal is heterogeneous product capability, not a second planner action manufactured for framework evaluation.

### Step 5 — pressure the richer core system with materially different existing cases

Use existing product-simulation evidence selectively to expose real next capabilities, for example targeted behavior-path investigation, contradiction-driven pruning, optional-environment formation, artifact/deployment context, or other independently useful evidence families.

Do not implement all cases or mechanisms for count alone.

### Step 6 — admit the next independently useful investigation capability only when product value earns it

The next capability must solve a real evidence/proposition problem on its own terms. Planner richness is a consequence, not the admission reason.

### Step 7 — framework experiment re-entry trigger

Resume richer LangGraph expansion, executable LangChain experimentation, and broader framework comparison only when evidence shows approximately:

```text
2+ independently admitted planner-selectable investigation capabilities
+
real states where several capabilities are plausibly useful
+
relative value/order changes with proposition state, prerequisites,
consumed history, failures, time/cost/resource budget
+
a small fixed deterministic policy becomes materially brittle,
duplicated, combinatorial, or semantically contextual
```

At re-entry, evaluate the frameworks against the richer real responsibility rather than replaying the current one-action experiment.

## 6. Current stop lines

Until the framework re-entry trigger is earned:

- do not add LangChain as an experiment dependency merely for exposure;
- do not build a generic LangChain tool loop;
- do not add a second planner action merely to make the planner look agentic;
- do not expand LangGraph with persistence, human approval interruption, subgraphs, parallelism, multi-turn loops, or generic tool machinery without a real product responsibility;
- do not integrate the current planner/LangGraph experiment into product runtime;
- do not treat framework capability lists as product need.

## 7. Immediate handoff

The next action in this session is the **LangChain relevance checkpoint**, followed by the joint framework-experiment closure/disposition.

Only after that closure should live work move back to the core impact/applicability/investigation responsibility and the unfinished artifact-serviceability application integration.
