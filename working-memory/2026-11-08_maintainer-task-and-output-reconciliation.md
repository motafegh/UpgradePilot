## Finding and proposed next responsibility

There is no missing action vocabulary or missing reviewer task list. The decision still worth making is which maintainer task drives the next delivery increment, what the first screen should help the maintainer recover, and how we will tell that it helped. Evidence fidelity and exact recovery are necessary delivery properties. They do not measure whether the normal report makes a decision-relevant finding easy to recover.

The [saved OpenCV report](evidence/2026-10-22-opencv-matched-report-source-capture/report.txt) illustrates the issue. It preserves a concrete publication change and unresolved target applicability, yet the action section begins with the evaluator's general `abstain` boundary. The [HTTPX baseline review](2026-11-07_evidence-grounded-maintainer-explanation_planning-cycle.md#httpx-concise-baseline-check) demonstrates that existing source evidence can support a concise answer that ties the conditional finding to the missing runtime premise. Its manual, case-exposed walkthrough did not measure navigation effort. The observed output supports a presentation hypothesis, not a reproduced usability defect or a justification for broad redesign.

Propose one primary task for the next delivery decision: **On this exact update, identify the strongest material finding, what it means for this repository, and what remains decision-relevant and unresolved.** A candidate human view leads with the update and evidence-backed finding, then its condition or blocker, then a specific decision-relevant observation if supported. Exact evidence links and the full report remain inspectable. An explanatory statement about what evidence would resolve an unknown carries no positive recommendation unless synthesis admits it. Display an action outcome separately with the explanation appropriate to its actual permission and implementation boundary. Prefer a short case-specific limitation over repeated generic boilerplate in the first view, with detailed limits still recoverable.

Before changing code, compare a concrete view sketch against the actual report using the existing reviewer questions. Use HTTPX for conditional source fit and OpenCV for publication versus target applicability. Include a stop/insufficient-evidence control so the sketch cannot gain clarity by overstating evidence. Judge correct task recovery, source opens or review burden where measurable, and any lost premise or invented action. If a layout using existing fields suffices, scope a presentation increment. If a needed fact or observation is missing, trace the earliest responsible owner. If there is no concrete improvement, preserve the result and defer. A new schema, action label or AI workflow has no demonstrated prerequisite here. Any positive action increment needs a separate real case with the required normal-producer proof.
