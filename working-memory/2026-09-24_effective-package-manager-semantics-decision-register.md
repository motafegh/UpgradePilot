## Purpose and learning checkpoint — agreed after onboarding

**Product goal:** strengthen UpgradePilot's existing Tree-sitter-backed workflow command analysis and exact CI runtime correlation to establish, for a supported case and justified observation boundary, that the **exact proposed dependency requirement is satisfied in the exact relevant Python package environment**. Current evidence can establish declaration/consumption and bounded successful command execution; that does **not alone** establish effective installing semantics, relevant package destination, or resulting proposed-version state. This work is **not** a general-purpose environment finder, full runner/shell simulator, or an attempt to prove every command in a job uses the same environment.

**Reuse and owner split:** Tree-sitter-backed workflow/shell analysis owns syntax, command occurrence, ordering, and source facts; dependency-owned pip/uv interpretation owns the effective package-manager operation and destination; exact CI runtime correlation owns its already admitted success relation; a separately designed package-state proof composition may combine them without inflating any source's claim. An admitted **Command-Derived Requirement-State Proof** concerns requirement satisfaction at **command completion**; **Direct Target-Owned Package-State Observation**, when available, concerns the package state **at its own observation boundary**. Later persistence, actual exact-version exercise, behavior/compatibility, and maintainer-action permission are separate propositions. See [runtime-state reconciled baseline](2026-09-24_runtime-state-reconciled-design-baseline.md), [package-state proof boundary review](2026-09-24_effective-semantics_state-proof-boundary-review.md), and [existing runtime-strengthening owner](../src/upgradepilot/ci/runtime_strengthening.py).

**User-agreed environment-identity principle:** Determine only the positively supported interpreter, *manager installation destination*, inspection scope, and consuming-environment relationships material to the **particular package/environment/time claim**. The four reviewed evidence families are legitimate candidate ways to prove such a relation, not mandatory sequential gates: explicitly resolved interpreter/destination; positively proven effective bare-executable selection; operation-specific pip/uv targeting; attributable target-owned environment/package-state observation. A command-completion state claim does not automatically require inspection or proof of a later test's interpreter. Same job/project, same `python` spelling, matching package/version, or literal path text alone is insufficient for an unqualified cross-process identity claim. An established different target defeats the attempted same-environment relation, not package presence. Missing material proof retains an expressive reason; the [four-layer explainable-uncertainty separation](#already-agreed--do-not-reopen-without-contradictory-evidence) remains distinct. **Agreement is to this proof boundary and supported-evidence direction, not to a finalized command/option catalog, concrete data schema, new state producer, or implementation authorization.**

## R2 closure map and depth discipline — finite, non-quota checklist

This checklist makes the remaining **Supported Subsystem Boundary Design** work visible without turning examples into a backlog or pre-creating speculative implementation cycles. The items are dependency-ordered checkpoints; a later checkpoint may collapse, shrink, or become unnecessary when earlier evidence is decisive.

1. **CLOSED FOR R2 BOUNDARY — normal `setup-python` → PATH → bare `pip`.** Provider ordering, action-step success, unnamed-step runtime identity, `GITHUB_PATH` precedence, and the declarative-`env` representation gap are understood at the boundary level; concrete evidence/type implementation remains for R3+.
2. **CLOSED FOR R2 BOUNDARY — bounded virtual-environment/PATH activation → bare `pip`.** The first supported CPython/Bash-sh family now has explicit positive premises, close defeaters, and a bounded sequential-reachability direction; exact evidence types/producer implementation remain for R3/R4+.
3. **CLOSED FOR R2 BOUNDARY — remaining normal interpreter / manager-target families.** Positive first-boundary families and recognized/deferred destination modifiers are selected using the three-dimension model `launcher/executor → manager-selected Python environment → final installation destination/scheme`; exact parser/type implementation remains R3/R4+.
4. **CLOSED FOR R2 BOUNDARY — effective operation/configuration semantics.** Use one demand-driven source precedence per material semantic dimension: CLI > effective process environment > applicable persistent configuration > manager default, with manager-specific config ordering and explicit source-disabling/replacement semantics. Defaults are never inferred through an unresolved higher-precedence source; only proof-critical dimensions are resolved. Exact source adapters/types remain R3/R4+.
5. **CLOSED FOR R2 BOUNDARY — first Command-Derived Requirement-State Proof (Route A).** The first positive family is an exact pinned requirements-file pip install into a positively resolved normal Python environment/destination with effective non-dry-run semantics and exact unmasked successful execution. It proves exact requirement satisfaction at command completion, not fresh-install causality or later use. Exact evidence types/implementation remain R3/R4+.
6. **CLOSED FOR R2 BOUNDARY — Direct Target-Owned Package-State Observation (Route B) and later-use scope.** Route B is optional/conditional. The first positive low-acquisition family is a self-verifying one-package `importlib.metadata.version(...)` check with positively resolved expected version, exact interpreter/environment identity, explicit nonzero failure semantics, and exact successful execution. Structured `pip inspect`/inventory outputs remain strong conditional sources requiring additional acquisition. Later-use claims require ordering + same relevant package-state scope + demand-driven material continuity + supported package consumption/invocation; none is a mandatory gate on Route-A command-completion proof.
7. **CLOSED — R2 supported boundary.** The first supported families, recognized-but-not-first-positive cases, reasoned unresolved cases, deferred capabilities, controlling-plan stop condition, and R3 producer/type/data-flow responsibilities are explicitly classified. Semantic exploration stops here unless contradictory evidence appears. The conditional explicit-runtime-state cycle is not selected; Route B remains an optional seam.

**Depth / rabbit-hole stop rule:** investigate a detail deeply only when its answer can materially change (a) correctness of the selected normal proof, (b) the supported boundary, (c) producer/consumer ownership or architecture, or (d) a decision-critical product capability. Otherwise preserve the case as unsupported/unresolved/deferred with provenance and continue. Do not investigate merely to eliminate every theoretical uncertainty.

**Program stop condition:** the controlling runtime-state plan requires **one trustworthy bounded positive command family with explicit close defeaters**, not universal Python/package-manager/environment coverage. Once that condition and the R2 boundary classification are satisfied, further semantic breadth must be justified by new evidence rather than curiosity or completeness pressure.

**After R2:** `R3 Evidence Source, Type, and Data-Flow Design → R4 Implementation and Proof-Sequence Planning / plan reconciliation → explicit Build authorization and implementation → real-case/regression verification → parent evidence-to-action integration`. These are responsibility gates, not a calendar or a required count of micro-investigations.

## Already agreed — do not reopen without contradictory evidence

- **Proposition-first, demand-driven investigation:** establish only facts material to the exact claim; decisive closer evidence need not trigger unrelated upstream reconstruction. [Reconciled baseline](2026-09-24_runtime-state-reconciled-design-baseline.md).
- **Claim-relative decisive-premise short-circuit (clarified in Stage 2):** for a *command-derived installation-state* claim, first establish whether any available applicable evidence conclusively defeats a necessary installing premise. In particular, positively established **effective dry-run for the exact pip process** means this command did not perform installation, so there is no need to resolve its target/destination merely to pursue installation proof through this command. A visible dry-run declaration that may be overridden is not a decisive finding; verify effective semantics before stopping. The command can have run successfully without installing, and this conclusion does not establish package absence or invalidate separate direct target-owned package-state observation. Preserve independently established source-bound facts; resolve destination if another claim actually needs it. This is **claim-relative proof dependency/early-stop ordering**, not a universal priority ranking between `--dry-run` and `--target`, and does not commit to a fixed evaluation algorithm or final pip/uv operation catalog. [Active proposition-relative semantic contract](2026-09-24_effective-package-manager-semantics-system-design.md); [package-state proof boundary review](2026-09-24_effective-semantics_state-proof-boundary-review.md).
- **Effective setting is not merely a visible declaration (clarified in Stage 2):** differentiate a command/step/job/workflow/configuration source value from evidence that it applies to and reaches the exact pip/uv process after material shell/process overrides. For the *particular required setting*, follow positively established applicable precedence backward and stop when the effective value is conclusively resolved; do not continue to lower-precedence sources just for completeness. Such a stop does **not** settle independent dimensions such as dry-run, destination, requirement selection or execution. Reuse this one provenance/precedence reasoning model across relevant options, rather than building one resolver per flag. [Existing environment-evidence learning and write/propagation boundaries](2026-09-22_b4-environment-evidence-data-flow-learning.md); [active proposition-relative semantic contract](2026-09-24_effective-package-manager-semantics-system-design.md).
- **Preserve source-bound facts even when downstream relevance is unproven (clarified in Stage 2):** successful command correlation is not automatically proof of package-state satisfaction; when exact requirement, effective operation/destination, success and the other admitted proof premises establish package state in a specific destination at command completion, retain that *bounded* finding with its provenance. A later consumer may use it only after the required environment visibility, timing and continuity relations are independently supported. An unrelated or unresolved later consumer relation does not invalidate the earlier state finding or prove package absence. For example, `--target ./vendor` does not by itself establish that a later Python process searches `./vendor`; the name `vendor` has no special pip meaning. [State-witness scope](2026-09-24_r2_state-witness-scope-checkpoint.md); [environment-identity review](2026-09-24_python-environment-identity_supported-boundary-review.md).
- **Strict claim boundaries:** command completion is not later persistence; observed presence is not proof of which command installed it, exact later version use, compatibility, or maintainer-action permission. No redundant inspection is required for a claim already proven at its own boundary. [State-witness scope](2026-09-24_r2_state-witness-scope-checkpoint.md).
- **Bare `pip` is a provenance problem, not a syntax-level rejection (clarified 2026-09-26):** preserve `pip install ...` as a potentially supportable normal command family. Resolve its package-environment identity from positive executable/environment provenance when available; otherwise leave that relationship unresolved rather than declaring the command itself unsupported or guessing the ambient interpreter. `actions/setup-python`, bounded virtual-environment/PATH selection, explicit interpreter paths, and `pip --python` are separate evidence relationships, not interchangeable shortcuts. The first supported boundary should target common positive relations rather than require `setup-python` universally. [Active subsystem design](2026-09-24_effective-package-manager-semantics-system-design.md); [environment-identity review](2026-09-24_python-environment-identity_supported-boundary-review.md).
- **`setup-python` PATH proof is conditional on its effective environment-update behavior (clarified 2026-09-26):** the normal `actions/setup-python` case is valuable because `update-environment` defaults to `true`, but an explicit/effective `update-environment: false` defeats only the inference that this action made its selected Python/pip the later bare executable. It does not make the action invalid, prove anything about another ambient `pip`, or justify rejecting bare `pip` globally. Such a configuration is more naturally paired with explicit use of the action's selected interpreter/output and is treated as an edge case unless real product evidence raises its priority. Preserve the general rule: reason from effective action/environment semantics, not merely the presence of a `uses: actions/setup-python` declaration. [Active subsystem design](2026-09-24_effective-package-manager-semantics-system-design.md).
- **Explainable uncertainty across distinct responsibilities (agreed 2026-09-24):** evidence assessment, evidence-gap reason, investigation disposition, and maintainer-action decision must remain separate, with expressive explanations and provenance. Preserve existing `established`/`refuted`/`unresolved`/`conflicted` and planner no-tool distinctions where applicable instead of introducing synonymous global status labels. This agreement is a design direction; exact reason codes and type schema are pending and it does not authorize model-driven execution or new maintainer actions. [Applicability model](../src/upgradepilot/impact/applicability.py); [planner experiment](../experiments/evidence_gap_planner_model_boundary.py); [current action evaluator](../src/upgradepilot/maintainer_action.py).
- **Naming and scope:** descriptive titles first; no artificially narrow flag-only product solution, no unsupported universal runner simulator, and **no Build authorization yet**. [Active design](2026-09-24_effective-package-manager-semantics-system-design.md).
