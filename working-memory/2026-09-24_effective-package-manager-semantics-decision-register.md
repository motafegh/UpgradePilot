## Purpose and learning checkpoint — agreed after onboarding

**Product goal:** strengthen UpgradePilot's existing Tree-sitter-backed workflow command analysis and exact CI runtime correlation to establish, for a supported case and justified observation boundary, that the **exact proposed dependency requirement is satisfied in the exact relevant Python package environment**. Current evidence can establish declaration/consumption and bounded successful command execution; that does **not alone** establish effective installing semantics, relevant package destination, or resulting proposed-version state. This work is **not** a general-purpose environment finder, full runner/shell simulator, or an attempt to prove every command in a job uses the same environment.

**Reuse and owner split:** Tree-sitter-backed workflow/shell analysis owns syntax, command occurrence, ordering, and source facts; dependency-owned pip/uv interpretation owns the effective package-manager operation and destination; exact CI runtime correlation owns its already admitted success relation; a separately designed package-state proof composition may combine them without inflating any source's claim. An admitted **Command-Derived Requirement-State Proof** concerns requirement satisfaction at **command completion**; **Direct Target-Owned Package-State Observation**, when available, concerns the package state **at its own observation boundary**. Later persistence, actual exact-version exercise, behavior/compatibility, and maintainer-action permission are separate propositions. See [runtime-state reconciled baseline](2026-09-24_runtime-state-reconciled-design-baseline.md), [package-state proof boundary review](2026-09-24_effective-semantics_state-proof-boundary-review.md), and [existing runtime-strengthening owner](../src/upgradepilot/ci/runtime_strengthening.py).

**User-agreed environment-identity principle:** Determine only the positively supported interpreter, *manager installation destination*, inspection scope, and consuming-environment relationships material to the **particular package/environment/time claim**. The four reviewed evidence families are legitimate candidate ways to prove such a relation, not mandatory sequential gates: explicitly resolved interpreter/destination; positively proven effective bare-executable selection; operation-specific pip/uv targeting; attributable target-owned environment/package-state observation. A command-completion state claim does not automatically require inspection or proof of a later test's interpreter. Same job/project, same `python` spelling, matching package/version, or literal path text alone is insufficient for an unqualified cross-process identity claim. An established different target defeats the attempted same-environment relation, not package presence. Missing material proof retains an expressive reason; the [four-layer explainable-uncertainty separation](#already-agreed--do-not-reopen-without-contradictory-evidence) remains distinct. **Agreement is to this proof boundary and supported-evidence direction, not to a finalized command/option catalog, concrete data schema, new state producer, or implementation authorization.**

## Already agreed — do not reopen without contradictory evidence

- **Proposition-first, demand-driven investigation:** establish only facts material to the exact claim; decisive closer evidence need not trigger unrelated upstream reconstruction. [Reconciled baseline](2026-09-24_runtime-state-reconciled-design-baseline.md).
- **Strict claim boundaries:** command completion is not later persistence; observed presence is not proof of which command installed it, exact later version use, compatibility, or maintainer-action permission. No redundant inspection is required for a claim already proven at its own boundary. [State-witness scope](2026-09-24_r2_state-witness-scope-checkpoint.md).
- **Explainable uncertainty across distinct responsibilities (agreed 2026-09-24):** evidence assessment, evidence-gap reason, investigation disposition, and maintainer-action decision must remain separate, with expressive explanations and provenance. Preserve existing `established`/`refuted`/`unresolved`/`conflicted` and planner no-tool distinctions where applicable instead of introducing synonymous global status labels. This agreement is a design direction; exact reason codes and type schema are pending and it does not authorize model-driven execution or new maintainer actions. [Applicability model](../src/upgradepilot/impact/applicability.py); [planner experiment](../experiments/evidence_gap_planner_model_boundary.py); [current action evaluator](../src/upgradepilot/maintainer_action.py).
- **Naming and scope:** descriptive titles first; no artificially narrow flag-only product solution, no unsupported universal runner simulator, and **no Build authorization yet**. [Active design](2026-09-24_effective-package-manager-semantics-system-design.md).
