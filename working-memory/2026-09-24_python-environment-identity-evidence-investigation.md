## Exact question

What positively establishes that the package manager's installation/satisfaction target, a subsequent target-owned installed-state inspection, and an eventual dependency-consuming command concern the **same relevant Python package environment**? Which such relationships does current UpgradePilot already produce, and what is missing?

A `requirements.txt` source path or `pyproject.toml` project root, a shared job, the literal name `python`, matching package/version text, and a green step do **not individually establish this identity**. Distinguish **dependency source/project selection**, **Python interpreter resolution**, **package installation destination and visibility**, **target-owned observation**, **later version continuity**, and **actual consumption/use**.

## Verified current source / implemented versus absent

- `src/upgradepilot/dependency/direct_install.py` + `dependency/workflow_context.py`: resolve static requirements-source and repository-relative working-directory relations, with step/job/workflow working-directory precedence. Their own contracts do **not** establish runtime process current directory, actual interpreter, target installation directory, or package state.
- `src/upgradepilot/dependency/environment_selection.py`: select a bounded project, extras/groups, and selected pip/uv project scope from static command occurrences. Its `project_root` and `working_directory` are project/source-context evidence, **not** proof of the exact interpreter/virtual environment used by installation, inspection, or a later test.
- `src/upgradepilot/dependency/pip_command.py`: `parsed_pip_install_arguments` currently admits literal `pip install`, `pip3 install`, `python -m pip install`, and `python3 -m pip install` prefixes. It does **not** admit an explicitly path-qualified `./.venv/bin/python -m pip install` or `python -m pip --python .venv install ...` in its current prefix pattern. The earlier illustrative explicit-venv installation must not be described as a currently supported end-to-end UpgradePilot command-state witness. Extension, if selected, belongs in the dependency interpreter/manager semantics layer with parser-neutral source observations rather than guessing via text downstream.
- `src/upgradepilot/github/workflow_definition.py` currently does not retain workflow/job/step `env` mappings; parsed shell occurrences do not yet expose typed complete process-identity/PATH/activation provenance. `src/upgradepilot/ci/runtime_strengthening.py` and `ci/dependency_exercise.py` establish bounded occurrence-to-exact-run-attempt/job/step reported-success evidence, **not** interpreter identity, installation destination, state persistence, or exact-version exercise. In particular, step success is not general proof that an arbitrary later command within that step executed.

## Confirmed external tool/process semantics relevant to identity

- `python -m pip ...` runs pip through that **selected Python interpreter**, whereas bare `pip` and bare `python` require justified executable resolution. pip's `--python` option can deliberately manage **another** Python interpreter/virtual environment, and pip install destination controls (`--target`, `--prefix`, `--root`, `--user`) can make an otherwise matching interpreter insufficient to prove relevant package visibility. Official: https://pip.pypa.io/en/latest/topics/python-option/ .
- Python virtual-environment activation typically changes the current shell's `PATH`; a separately started GitHub Actions `run` step has a **new shell/process**, so source-visible `source .venv/bin/activate` in one step does not prove an unqualified `python` in the next step selects that environment. Explicit interpreter paths or positively established effective `PATH`/process observations are stronger. `sys.executable` and `sys.prefix` reported by the **actual target process** are useful runtime interpreter/environment facts, but a value printed elsewhere or in another attempt/job is not. Official: https://docs.python.org/3/library/venv.html ; https://docs.python.org/3/library/sys.html ; https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax .
- GitHub step/job/workflow env scope, positively established `GITHUB_ENV` updates, and `GITHUB_PATH` updates can affect **subsequent same-job steps**; source visibility is not executed mutation and neither file updates the writing step. Opaque setup actions, dynamic PATH edits, unknown runner state, custom wrappers, and later changes are unresolved when material. Official: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands .
- uv normally uses a project virtual environment, with project/workspace selection and `UV_PROJECT_ENVIRONMENT` capable of changing its location; `uv run` selects a project execution environment, while isolated execution, `--with` overlays, `--active`, `--no-sync`, and possible environment synchronization must be interpreted before equating a `uv sync` destination, a plain `python` inspection, and a later invocation. Project root sameness alone is insufficient. Official: https://docs.astral.sh/uv/concepts/projects/layout/ ; https://docs.astral.sh/uv/concepts/projects/config/ ; https://docs.astral.sh/uv/concepts/projects/run/ .
- `pip inspect` is a JSON report of installed distributions in its selected Python environment, but the mere presence of JSON/package/version does **not** provide proof of the invoking executable or equate it with the install/test environment; its `environment` object contains packaging environment markers, not automatically a unique virtual-environment identifier. Inspection options such as `--path` may further scope which packages are listed. Official: https://pip.pypa.io/en/latest/cli/pip_inspect/ ; https://pip.pypa.io/en/latest/reference/inspect-report/ .

## Candidate evidence boundary for review (NOT YET SELECTED)

1. **Start from the exact claim and nearest sufficient witness.** For command-completion state, resolve the package-manager process's effective Python/package destination and show its positively established relation to the selected dependency-consuming environment; do not require a later inspection automatically. For direct observed state, bind actual target-owned output to the exact run attempt, job, executed observation occurrence and the environment/package scope it inspected. Do not infer how it got there.
2. **Seek positive environment-equivalence evidence, not textual similarity.** Candidate strong cases: positively resolved explicit interpreter/destination references within the same run-attempt/job/workspace; known manager project-environment rules with all material selection/override inputs resolved; or exact target-emitted interpreter/environment fingerprints (such as `sys.executable`, `sys.prefix`, relevant package metadata location) associated with **each relevant executed process**, interpreted with their provenance. An explicit path is not sufficient if its runtime resolution, destination, process overrides, or time-scoped continuity remain material and unproved. Fingerprints are candidate evidence **when already emitted**, not a new requirement to modify public target workflows.
3. **Resolve only material incoming relations.** Where bare `python`/`pip` is used, follow proven process-local executable resolution, workflow/job/step env, relevant `PATH`/`GITHUB_PATH` changes and shell-local activation, and manager targeting as needed. A resolved near-process explicit target can make irrelevant upstream environment unknowns unnecessary; a still-material opaque setup action, variable, mutable path, foreign container/job, or ambiguous selection must remain unresolved. Avoid a universal runner/PATH/operating-system simulator.
4. **Keep three distinct edges:** same *package destination/visibility* at the witness boundary; same *environment* at a later observation/exercise; same *proposed version actually consumed* by the later exercise. Earlier state alone does not establish later persistence or use. Preserve the existing claim's exact environment/time/source and represent the missing relationship instead of claiming package absence or compatibility.

## Concrete review example

```text
Step 1: ./.venv/bin/python -m pip install -r requirements.txt
Step 2: python -m pip list --format=json  # reports proposed ruff version
```

Within a successful same-job run, Step 2's unqualified `python` may select system Python instead of `.venv`; the inspection may truthfully report ruff in **that different environment**. Step 1's explicit interpreter form is **not currently recognized** by UpgradePilot's pip-prefix parser. Until source/runtime facts establish both commands' environment/destination identities and their relation, no cross-step same-environment proof is earned. If Step 1 instead uses the *currently recognized* `python -m pip install -r requirements.txt`, it still requires evidence of which `python` was selected and whether any installer destination override applied. Package presence reported at inspection time is separate from later exact-version use.
