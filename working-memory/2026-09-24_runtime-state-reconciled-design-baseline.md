**Purpose:** one compact, retrievable map of what UpgradePilot has already implemented, accepted, investigated, and still needs to design. This working-memory reconciliation is **not** a replacement for controlling specs/ADRs/plans, earlier investigations, or `MEMORY.md`'s live-state authority.  
**Active detailed record:** [Effective package-manager semantics system design](2026-09-24_effective-package-manager-semantics-system-design.md).  
**Goal — explicit user direction:** find, design, and build the **proper and smartest coherent system** for real UpgradePilot effective package-manager semantics and runtime dependency-state proof. Do **not** optimize the architecture for being the “smallest,” reduce it to an easy flag-only patch, or use an insufficient partial patch as an automatic reason to stop building. Keep scope product-faithful and evidence-grounded, not an unrelated universal simulator.

## 1. Established product/evidence ladder

```text
exact dependency/version and source
→ exact selected dependency environment and static consumption
→ exact command/step runtime correlation and reported success
→ effective package-manager semantics + relevant environment/destination relation
→ exact proposed-version state at a justified observation boundary
→ separately proven same-version use by a later exercise, if required
→ separately evaluated behavior / maintainer-action permission
```

Each arrow needs independently justified evidence. Static declaration != execution; correlated success != installed version; state at command completion != persistence; package presence != exact version used by a later test; green CI != compatibility or maintainer permission. A command-specific defeater defeats *that inference*, not proof that the package is absent. [Earlier dependency/CI proof ladder](../plans/B2_DEPENDENCY_ENVIRONMENT_AND_CI_CONSUMPTION_EVIDENCE_PLAN.md); [F6 state and exercise boundaries](2026-09-21_f6-post-install-package-state-feasibility.md).

## 3. Previously established semantic surface

Material pip/uv families: mutation/sync (`--dry-run`, `--no-sync`, `PIP_DRY_RUN`, `UV_NO_SYNC`); relevant package/group/root exclusions; retargeting (`--target`, `--user`, `--root`, `--prefix`, uv environment/project selection); invocation overlays/version overrides; configuration-loading and ambient `PIP_*`/`UV_*`; environment/interpreter/destination identity. Relevance is relative to the **exact changed-package state proposition**. Later mutation belongs to the temporal handoff to a later observation/exercise, not to command-completion semantics. [Cycle-1 investigation](2026-09-21_runtime-install-command-semantic-eligibility.md).

**Accepted B4 reasoning model:** for each required dimension, start at the exact pip/uv process; use decisive process/CLI evidence if established, else trace shell-local assignments → applicable step environment → positively proven same-job `GITHUB_ENV` updates and job/workflow environment → applicable observable manager configuration, only as far backward as needed. The most recent *proven applicable* write matters; a later potentially relevant but execution-unresolved write cannot simply be ignored. Higher-precedence decisive evidence may render lower-precedence unknowns irrelevant **for that dimension only**. Missing/unproved edges remain `unresolved`. [B4 graph, write, precedence and backward analysis](2026-09-22_b4-environment-evidence-data-flow-learning.md).

**Accepted owner split:** GitHub workflow/shell evidence owns declarations, source order, scope, propagation and exact-process value relationships; dependency/pip/uv owns manager semantics; CI/state-proof composition owns runtime correlation and proof conclusions. Do not turn Tree-sitter or generic runtime correlation into the pip/uv semantic owner. [ADR-0008](../docs/architecture/ADR-0008-bounded-static-github-actions-workflow-definition.md), [Cycle-1](2026-09-21_runtime-install-command-semantic-eligibility.md).

**Accepted B5 command-derived claim:** exact proposed dependency/source + exact relevant environment + static consumption occurrence + admitted command-local semantics + fully non-defeating effective dimensions + exact successful runtime occurrence + the applicable manager-operation guarantee may establish **requirement satisfied/present at that command-completion boundary**. This does not prove fresh installation, selected artifact, subsequent persistence/use, behavioral compatibility, or any maintainer action. [Cycle-1 B5](2026-09-21_runtime-install-command-semantic-eligibility.md).

## 5. Genuine open design and proof questions (R2 → R3)

1. **Supported evidence boundary:** which command, workflow/job/step `env`, shell assignment/export, positively proven `GITHUB_ENV` write/propagation, manager config, and target/interpreter relation shapes can establish effective values in *normal real* pip/uv paths? Specify opaque/dynamic/external cases that remain unresolved **only when material**.
2. **Backward proof realization:** how do we preserve necessary process-near value, scope/order, precedence, provenance and unresolved edges without duplicating the existing parser, CI correlator, or building an unneeded general graph/runner simulator? Resolve the gap where parsed command occurrences and workflow IR do not yet supply needed environment facts.
3. **Proof-route architecture:** determine whether command-derived completion-state inference and independent target-owned installed-state observations are separate typed paths composed into a common exact-state proposition, and how installer reports remain distinct from observed inventory. Preserve their **different observation-time claims**.
4. **Real applicability and tests:** pressure-test the chosen architecture on real normal pip/uv cases and close defeaters; establish exact process/step identity and actual run evidence. A later-in-step command must not inherit step-success proof currently admitted only for a sole/first eligible command.
5. **Downstream integration:** retain data needed for future version-to-exercise binding, but do not duplicate implemented static order/runtime correlation or silently claim later persistence/behavior. Reconcile master-plan sequence and action-relative value explicitly before Build.

**Next focused work:** review the already-recorded R2 candidate against these gaps and source truth; decide the coherent *supported evidence and proof-route boundary*, then R3 designs concrete types, owners and data flow. No product code, tests, stable specifications, ADRs or plan semantics were changed by this reconciliation.

## 6. Current discussion — decisions, corrections, learning, and unresolved points

This section preserves the distinctive findings from the September 24 design/learning discussion without turning the record into a chat transcript. See the [active detailed design record](2026-09-24_effective-package-manager-semantics-system-design.md) for the current R2 candidate and [F6](2026-09-21_f6-post-install-package-state-feasibility.md), [Cycle 1](2026-09-21_runtime-install-command-semantic-eligibility.md), and [B4 data-flow learning](2026-09-22_b4-environment-evidence-data-flow-learning.md) for earlier source-backed detail.

- **USER DIRECTION / GOAL — explicit:** “proper and smartest” replaces “smallest” as our architecture-design target. Build a useful coherent system for normal real cases, not a narrow set of `--dry-run`/`--no-sync` checks. An insufficient quick patch is reason to work out the right system, not by itself a decision to defer the product capability. This instruction does not waive evidence quality, existing governance, plan ownership, or the Build review gate. The [active detailed record](2026-09-24_effective-package-manager-semantics-system-design.md) also captures the revised intent.
- **RECONCILIATION — previous decisions still matter:** B6 selected no *partial Cycle-1 Build*, not a permanent prohibition on an integrated capability. Earlier B1–B5, B4 environment-flow graphs, and F6 observation/temporal requirements are existing work to reuse; design must not silently reinvent them. [Cycle 1](2026-09-21_runtime-install-command-semantic-eligibility.md); [B4](2026-09-22_b4-environment-evidence-data-flow-learning.md); [F6](2026-09-21_f6-post-install-package-state-feasibility.md).
- **LEARNING CHECK — precedence, with precise claim limit:** in an admitted simple step, workflow `PIP_DRY_RUN=1` and step `PIP_DRY_RUN=0` result in the step-level value `0` under the declared-env specificity rule. That establishes `resolved_non_defeating` for the *dry-run dimension only* if the exact process value is justified and no later shell/command override applies. An explicit pip `--dry-run` defeats command-as-state-proof even with that inherited value. No individual dimension proves installation/state by itself. [B4 scope/overrides/precedence](2026-09-22_b4-environment-evidence-data-flow-learning.md); [Cycle-1 B4](2026-09-21_runtime-install-command-semantic-eligibility.md).
- **ACCEPTED PRIOR STRATEGY — backward with graph explanations:** start from the exact proposition and strongest process-near evidence; trace shell, step, same-job writes, workflow/job environment or manager config backwards *only when material*. Top-down graph/data-flow reasoning diagnoses possible propagation and missing edges; graph diagrams and one-variable transfer functions do **not** select a general graph engine, CFG, SSA, or runner simulator. A source-visible `GITHUB_ENV` write is not a proven executed write; a proven write reaches later same-job steps as a baseline, not automatically the exact pip process. [B4 graphs, follow-ups and explicit “backward / demand-driven proof strategy” heading](2026-09-22_b4-environment-evidence-data-flow-learning.md).
- **CANDIDATE, NOT SELECTED — two independent proof routes:** command-derived state at the command-completion boundary *or* direct target-owned installed-state observation at its own observation boundary; installer activity/report evidence has distinct strength from installed inventory. Identical exact package/version text from different source types does not make their temporal or environment claims interchangeable. This concept was already explored in F6; the current R2 record revisits how to compose it without requiring universal reconstruction. [F6 §§6–9](2026-09-21_f6-post-install-package-state-feasibility.md); [R2 candidate](2026-09-24_effective-package-manager-semantics-system-design.md).
- **CORRECTION — version-to-exercise is not a newly discovered subsystem:** discussion of checking the installed distribution versus invoking `python -m ruff --version` was a teaching example of witness-to-exercise identity. A version report, the same invocation path/interpreter, suitable ordering, exact runtime evidence, and absence of unaccounted material intervening change may be relevant; `importlib.metadata.version` reports an installed distribution for its interpreter but by itself does not prove which executable a later invocation used. The architecture/claim limits were already identified in the B2 proof ladder and F6 §§7–9. Reuse existing static order and runtime correlation; do not automatically extend today's R2 scope to downstream version-use proof. [B2 dependency/CI plan](../plans/B2_DEPENDENCY_ENVIRONMENT_AND_CI_CONSUMPTION_EVIDENCE_PLAN.md); [F6](2026-09-21_f6-post-install-package-state-feasibility.md); [current CI composition](../src/upgradepilot/ci/dependency_exercise.py).
- **OPEN — selection and Build route:** finish R2 by comparing the existing candidate against current source, normal real-case evidence, precedence/propagation unknowns, and the F6 action-relative need; then design the concrete R3 evidence types/owners/data flow and reconcile the master plan if the selected route changes its scope or cycle sequencing. The earlier accepted proof contracts are not a claim that this new implementation is already built, that Route B is already selected, or that R2 is complete.
