**Branch:** `learning/semantic-comparison-d-prep-2026-10-18`  
**Companion:** `working-memory/2026-10-18_semantic-comparison-phase-D-learning-preparation.md`  
**Purpose:** prevent the Phase D preparation/learning journey from expanding into unnecessary rabbit holes while preserving the depth needed for genuine learner ownership.

## Controlling rule

Phase D targets **decision-relevant mastery, not exhaustive study**. Go deeper only when the missing depth would materially affect one of these outcomes:

1. understanding the current architecture or authority boundary;
2. tracing/debugging an actual code or evidence path;
3. interpreting the semantic comparison correctly;
4. distinguishing what the evidence proves from what it does not;
5. making or supervising a concrete project decision.

If additional detail does not materially improve one of those five outcomes, record it as optional/deferred rather than expanding the active learning block.

## Stop lines

For each D block:

- Prefer **one representative end-to-end trace** over reading every related function or fixture.
- Prefer **one or two decisive edge cases** over cataloguing every possible variant.
- Read code at the responsibility/logic level first; descend into implementation minutiae only when required to explain a mechanism or resolve a real uncertainty.
- Do not reopen concepts already demonstrated at sufficient depth unless new B evidence materially changes them.
- Do not study deferred runtime optimization, unrelated product families, framework alternatives, multi-agent designs, or other architecture branches unless the final B result makes them decision-relevant.
- Do not turn the 53 preparation questions into 53 separate lessons. Group overlapping questions under the smallest coherent learning block.
- Do not require perfect recall of names, hashes, file paths, or every test. We must know how to locate and verify them.
- A learning gap may be explicitly deferred when it is non-blocking for the semantic result or next project decision.

## Block completion heuristic

A block is sufficiently complete when we can:

1. explain the core mechanism in our own words;
2. trace one representative real project path to the relevant code/evidence;
3. state its authority/proof boundary;
4. diagnose one representative failure or edge case;
5. connect it to the semantic comparison or next decision.

We do **not** keep digging merely because more technical detail exists.

## Journey compression

The D0-D9 structure is an organizational map, not a requirement for ten long sessions. Combine adjacent blocks when they naturally reinforce each other. The expected compact path is:

`orientation + architecture -> one end-to-end code/reference trace -> v2/budget/qualification mechanics -> fairness + semantic-review method -> final B result interpretation -> learner synthesis`

D8 remains outcome-dependent and should absorb any new mechanisms introduced by B rather than causing the earlier blocks to restart wholesale.

## Rabbit-hole trigger

Before opening a deeper subtopic, answer:

> What current misunderstanding, proof risk, semantic-review risk, or project decision will this additional depth resolve?

If there is no concrete answer, defer it.

## Time/effort posture

Use short, progressive sessions with explicit stop points. When the mastery heuristic is satisfied, move on even if optional details remain. Preserve optional questions in a deferred list rather than blocking D closure.

The final standard is not exhaustive knowledge; it is the ability to independently understand, audit, explain, and make evidence-disciplined decisions about the completed semantic-comparison cycle.
