# Deferred research: peer-package constraint consistency versus uv reachability

**Recorded:** 2026-11-14. **Status:** Research/design candidate only; not an accepted Build, specification, architecture decision, or change to the live next action.
**Origin:** [ApplyPilot/pyee real case analysis](ANALYSIS.md), [verified case evidence](RESULTS.md), and follow-up supervision/learning discussion. **Provenance:** `UP-SKILL:upgradepilot-working-memory` and `UP-SKILL:upgradepilot-planning-design`.

## The observed distinction worth retaining

**A. Failed CI consuming step versus aggregate explanation — already selected immediate repair.** The existing CI runtime correlation and workflow evaluator admitted an exact dependency-consuming install step that **completed unsuccessfully**. The current top-level `evaluate_dependency_ci_coverage` explanation sometimes falls through to a generic `dependency_consumption_not_established` message because it notices a successful *sibling job* and loses the workflow's precise unsuccessful-consumption result. This is a **report/aggregation defect**, not evidence that the product counted only successful jobs or that pip's failure cause is known. The existing selected disposition is `bounded_build:ci.dependency_exercise_aggregate_consuming_step_explanation`. Fix and test this **separately**, retaining negative execution evidence, no successful consumption credit, no invented failure causality and the current action boundary. See [original diagnostic](ANALYSIS.md).

**B. Transitive dependency reachability — already implemented in a bounded uv-specific form.** `src/upgradepilot/dependency/uv_lock_structure.py` admits exact `uv.lock` structure; `uv_lock.py` establishes supported version transitions; `uv_reachability.py` follows admitted exact-lock edges from *explicitly selected uv roots* and can emit `reachable` with `direct` or `transitive` witness path, `not_established` for a completely traversed bounded root domain, or `unresolved` for markers, forks, selector/workspace scope or traversal limits. `src/upgradepilot/ci/consumption.py` maps these to static changed-dependency-consumption evidence without turning that into runtime execution. **This is not a generic solver, whole-workspace dependency graph, lock freshness check or cross-package version-consistency proof.**

**C. Peer-package version constraint consistency — not generally implemented by the ordinary investigation.** The frozen ApplyPilot PR proposes `pyee==16.0.1` while its unchanged peer pin is `playwright==1.64.1`; the latter's published `Requires-Dist` declares `pyee>=13,<15`. Under those metadata and normal dependency resolution, the two exact pins are **declared-incompatible**; the old `pyee==14.0.0` satisfies that range. This is independent of whether the selected historical pip step failed *because of* that conflict: the exact step error log was not acquired. The ordinary source path currently does not collect unchanged peer pins and compose version-scoped peer metadata. The opt-in caller/signature adapter already parses `Requires-Dist` for its own bounded purpose; reuse should be evaluated rather than assumed.

## Questions to answer before a new plan or Build

1. **Value:** Does reporting an exact peer-pin contradiction materially change a maintainer's next check beyond the current artifact/CI/LLM report? Compare the retained ApplyPilot positive conflict against a closely matched *compatible* control and an incomplete-metadata case; report false positives, abstentions, source effort and useful decisions.
2. **Minimal deterministic baseline:** From the exact changed dependency and relevant unchanged peer pins in the selected target environment, acquire version-scoped authoritative `Requires-Dist` metadata and evaluate exact version specifiers using Python's `packaging` library. Record the target's Python version/platform, selected extras/groups, environment markers, index/source identities and metadata/provenance. Avoid claiming global satisfiability when only selected peers are inspected.
3. **Resolver reference, not a replacement engine:** Compare this narrow static check with a properly bounded, isolated invocation of an established resolver such as `uv` or pip dry-run for matching input semantics. Use Poetry only where the target's actual project format and configuration make it representative. Capture exact tool version, arguments, index/config/env, requested package pins, network activity and result. A resolver's successful outcome has its own environment and index horizon; it is **not proof of runtime import, behavioral compatibility or historic CI exit cause**. Resolver commands may fetch metadata or invoke build backends: **do not run arbitrary target code, mutate the target environment or rely on unsafe metadata generation** without separate execution/security authorization.
4. **Coverage boundary:** Decide how to handle extras, marker-dependent requirements, alternative indexes, wheel/sdist metadata variance, direct URLs, source edits, multiple resolution branches, partial peer enumeration, and constraints/lockfile formats. Uninspected or conditional peers must remain `unresolved`, not `compatible`.
5. **Product ownership:** If evidence establishes usefulness, write a **separately authorized** narrow investigation/design plan for selected-peer constraint consistency; reuse `package_identity`, version-scoped metadata parsing, source IDs and report contracts where appropriate. Preserve strict separation among `declared_conflict`, `resolver_outcome`, `observed_failed_CI_step` and `causal_CI_failure`. Don't import this into the already-selected CI aggregate explanation repair.

## Non-decisions and handoff

- **No decision yet** that generic transitive satisfiability analysis, an external solver integration or a new report schema is warranted.
- **No assumption** that uv's existing selected-root reachability proves compatibility of peer pins; ApplyPilot is a `requirements-lock.txt` case, not a `uv.lock` graph case.
- **Do not amend the accepted cross-profile plan** merely to append this optional feature. This note remains a retrievable design hypothesis linked to its original real-case evidence.
- The **immediate next work** remains the independently selected, narrow failed-step CI aggregate explanation correction, subject to its own Build authorization and test/learning gates. Recheck `MEMORY.md` for the then-current continuation before starting any follow-up research.
