**Recommended next responsibility:** a bounded Planning/Design review of a deterministic API call/signature evidence baseline under the existing [API/source trial](../../../plans/UPSTREAM_API_CHANGE_AND_TARGET_EXPOSURE_FEASIBILITY_PLAN.md), with the accepted [responsibility-decomposition proposal](../../../proposals/2026-10-19_INVESTIGATOR_RESPONSIBILITY_DECOMPOSITION_AND_PRODUCT_DIRECTION_PROPOSAL.md) as rationale. No new master plan or framework is warranted. Prefer a compact complete action contract in that owner's normal design/evidence surface when feasible.

The design should answer one consumer question: **what exact arguments does a captured caller explicitly supply, what does a qualified captured callee explicitly accept, and which missing dispatch/version/source premise prevents interpreting their relationship?** Output must distinguish observed call/signature facts from a conditional relation and a claim about the actual target. Source facts can constrain later attributed analysis; they do not create compatibility or action permission.

Full relevant responsibility includes behavior changes, wrappers/dynamic dispatch, target resolution, environments and runtime effects. The proposed first design covers explicit structural evidence and honest unresolved relations only. Its narrower scope is justified by the demonstrated false source assertions and existing bounded AST machinery; it is not complete API-impact analysis. Dynamic expansion, super dispatch, positional/keyword rules and incomplete snippets must be examined before selecting the supported subset rather than silently treated as solved.

Before Build, qualify actual retained source bytes/identity/completeness, inspect reuse of existing keyword/binding records, settle callee/signature representation and caller↔callee association, identify a concrete consumer, select discriminating positive/negative/unknown cases and define failure/cost/adoption limits. No package-specific app/cert rule, synthetic-only acceptance, new truth-state enum, generic graph solver, model call, target execution or normal-product migration follows automatically. If existing records already supply an adequate baseline, prefer reuse; if retained sources cannot support the question, record the missing premise instead of fabricating a relation.

**Strongest counterargument:** another structural mechanism could improve laboratory correctness while leaving normal acquisition and maintainer value unchanged. Therefore require a thin consumer-facing evidence example and an explicit path/limit for normal inputs; reject a generic parser programme or inventory-only success. Design may conclude reuse, narrow, defer or stop. Independent usefulness remains a separate question throughout.
