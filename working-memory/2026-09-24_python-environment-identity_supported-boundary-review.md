## Precise claim and terminology

For **Command-Derived Requirement-State Proof** (historical Route A), ask whether the manager operation, with positively established effective semantics and exact execution success, makes the **proposed requirement satisfied at command completion in the exact relevant package environment**. For **Direct Target-Owned Package-State Observation** (historical Route B), ask whether an actually executed inspection, with attributed output, establishes installed-distribution presence **in the environment/scope observed at the observation boundary**. A later test-use claim requires separate applicable continuity and consumption proof; no redundant inspection is needed merely to restate an already proved command-completion claim.

Distinguish (1) **launcher** — executable/process invoking pip or uv; (2) **manager target/destination** — environment or directory actually managed by the operation; (3) **observed package scope** — environment and filters of an inventory; (4) **selected consuming environment** — where the proposed-version claim is needed; and (5) **later process/import resolution** — what a test actually used. A matching interpreter executable/path, package name, project root, CI job, or version string by itself does not imply all these relations or later persistence. Same interpreter prefix does not resolve `--target`, `--user`, custom import paths, visibility filters, or command-specific overlays.

## Verified source and real-case pressure

- **Current code boundary:** `src/upgradepilot/dependency/pip_command.py` recognizes bounded literal `pip[3] install` and `python[3] -m pip install` prefixes, not a path-qualified `./.venv/bin/python -m pip install` or the `python -m pip --python .venv install` global-option form. `dependency/direct_install.py`, `dependency/environment_selection.py`, and `dependency/workflow_context.py` own source/project/working-directory declarations, **not runtime interpreter or destination identity**. `github/workflow_definition.py` currently lacks typed workflow/job/step `env:` fields, and `ci/runtime_strengthening.py` establishes only admitted exact-command runtime-success relationships. Do not claim any proposed new environment proof is already implemented. See source at `src/upgradepilot/dependency/pip_command.py`, `src/upgradepilot/dependency/environment_selection.py`, `src/upgradepilot/github/workflow_definition.py`, and `src/upgradepilot/ci/runtime_strengthening.py`.
- **Real reachable evidence:** [prior Aruba Dependabot-PR investigation](2026-09-21_f6-post-install-package-state-feasibility.md#3-real-public-evidence--normal-upgradepilot-shaped-positive-case) records real `python3 -m pip install -r requirements.txt` followed by `python3 -m ruff ...` in an exact-head successful job, with an installer log reporting the proposed version. This demonstrates a normal supported-prefix workflow and package-manager output, **not by itself a positive cross-step interpreter identity or exact-version-use proof**. Existing evidence and current source were reviewed; no new live target run or test was executed for this checkpoint.
- **pip:** `python -m pip --python .venv install ...` manages `.venv` even though pip was launched through another interpreter. `pip install --target`, `--prefix`, `--root`, and `--user` can change installation destination/visibility. Bare `pip` or `python` require evidence of executable selection. Official: https://pip.pypa.io/en/stable/topics/python-option/ ; https://pip.pypa.io/en/stable/cli/pip_install/ .
- **uv requires operation-specific interpretation:** uv project operations normally select a project environment; `UV_PROJECT_ENVIRONMENT` and `--active` can change its destination/selection. Conversely `uv pip install`/`uv pip list` follow uv's pip-interface environment-discovery rules; `uv pip install --python`, `--system`, `--target` and an active virtual environment may change its target. `uv run` may synchronize/modify its environment and may use an invocation overlay. Do not equate `uv sync`, `uv pip list`, and plain `python` merely from shared project root. Official: https://docs.astral.sh/uv/concepts/projects/config/ ; https://docs.astral.sh/uv/concepts/projects/run/ ; https://docs.astral.sh/uv/pip/environments/ ; https://docs.astral.sh/uv/reference/cli/ .
- **Python/Actions:** explicit interpreter paths, or actual target-emitted `sys.executable`/`sys.prefix` observations, can help identify a relevant process, but require source/job/step attribution and context. `sys.path`/`PYTHONPATH` and virtual-environment inheritance can affect package visibility independently of interpreter prefix. `GITHUB_PATH` affects later same-job steps, not its writer; a source-visible write is not execution proof. Bare `python` in a new step does not inherit a previous step's shell-local activation automatically. Official: https://docs.python.org/3/library/sys.html ; https://docs.python.org/3/library/venv.html ; https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands .
- **Direct reports:** `python -m pip inspect` can establish installed distributions under its observed interpreter/scope; `--path`, `--user`, and `--local` narrow that scope, and its JSON environment-marker field is not a unique virtual-environment identity fingerprint. Inspect output alone neither identifies the exact invoking executable nor proves a different process used that version. Official: https://pip.pypa.io/en/stable/cli/pip_inspect/ ; https://pip.pypa.io/en/stable/reference/inspect-report/ .

## Candidate supported evidence families and decisions to review

| Supported candidate | Positive evidence required for the exact claim | Stop line when absent |
| --- | --- | --- |
| **Explicit interpreter / destination** | Exact parsed command and relative-path context, applicable run attempt/job/workspace and known operation-specific destination, with material overrides excluded/resolved; e.g. an explicitly resolved `.venv/bin/python -m pip` target **once command recognition is implemented**. Identical path strings across time do not alone prove the same environment still exists or is unchanged. | Ambiguous path, recreated or mutated environment when temporally material, or unsupported prefix → unresolved for the stronger claim. |
| **Effective bare executable selection** | Positive process-near executable selection: relevant literal step/process `PATH`, a proven `GITHUB_PATH` update, within-step activation/export, or attributable target-owned runtime executable evidence. Follow provenance and precedence only as far as the material edge requires. | An opaque `setup-python` action, shell wrapper, runner-host `PATH`, or mere same spelling `python`/`python3` is not automatic interpreter identity. |
| **pip / uv operation-specific targeting** | Manager-aware interpretation of the exact install/sync/run/inspect operation and relevant target options, project/root selection, configuration and effective environment; distinguish launcher from manager target, installed destination from inspectable import scope. | Unknown applicable `--python`, `--target`, `--user`, `--prefix`, `UV_PROJECT_ENVIRONMENT`, uv pip discovery, isolated/overlay state, or import-path relationship → unresolved where material. |
| **Actual target-owned environment/state witness** | Already available, positively attributed exact-run/attempt/job/occurrence output, identifying its interpreter/environment, inspected distribution/version, any scope filters and observation position. May independently establish **observed state** without retroactively proving installer targeting or success. | Visible inspection command or job success without actual attributed output is not a package-state observation. A `pip inspect` environment-marker JSON field is not by itself environment identity. |

**Candidate evaluation result:** Resolve only the identity/visibility relations material to the proposition, using the closest decisive positive source. Preserve per-process launcher, target, observation scope, environment relation, timestamp/ordering boundary, evidence provenance and unresolved reasons without selecting concrete classes or a universal shell/runner emulator yet. An explicit positively different environment defeats **the attempted same-environment relation**, not the claim that the package is absent: shared/system site packages, custom `PYTHONPATH`, or a direct consuming-process witness may separately establish visibility. For a direct observation already inside the exact relevant consumer environment, do not demand reconstruction of how it got there.
