# 3. CAND-02 — resolver/currentness/satisfiability

## 3.1 Strongest deterministic baseline

A strong deterministic policy can already be written conceptually without hardcoding S007:

```text
IF the owned declared-constraint/currentness proposition is already established/refuted
    → do not resolve

ELSE IF a cheaper/stronger already-admitted authoritative source can deterministically
        establish/refute the proposition
    → consume that source/result first
    → re-evaluate

ELSE IF exact resolver context is unavailable/unsafe/unbound
    → unresolved or defer

ELSE IF the same definitive resolver investigation was already consumed
    → do not blindly repeat

ELSE IF budget admits the check
    → run one bounded exact resolver/currentness check
    → deterministically interpret established/refuted/unresolved

ELSE
    → stop/defer/unresolved according to the bounded question
```

This is not obviously complex enough to require an LLM.

### Existing evidence supporting this baseline

AUDIT-004 already defines resolver satisfiability as a distinct proof rung and preserves exact claim limits.

S007 gives a concrete pruning example:

```text
T1
package-family coherence unresolved
→ isolated resolver dry run looked useful

T2
trusted official TorchVision release-build contract
+ deterministic constraint intersection
→ package-family formation refuted
→ resolver dry run no longer worth executing
```

S007's frozen selection artifact explicitly records that expected resolver failure would only corroborate an already-established contradiction, while unexpected success would create a conflict.

This is genuine information-value reasoning, but a deterministic rule can express the observed S007 policy.

## 3.2 Where planner value could still exist

The unresolved planner-value question is not:

```text
can an LLM notice that resolver evidence may help?
```

It is:

```text
when several independently admissible investigations exist,
can the planner choose/sequence the one with the highest current discriminating value
without encoding one mechanism-specific ordering rule per case family?
```

Potential state dimensions include:

- exact static package metadata available or not;
- exact lock currentness known or not;
- several target environment scopes/extras/groups;
- resolver context sufficiently bound or still prerequisite-dependent;
- artifact-serviceability question coexisting with constraint-satisfiability question;
- previous resolver problem/transport failure versus definitive resolver result;
- remaining step/cost budget;
- one action becoming stale after another result;
- question already settled by a different evidence branch.

Current S001/S002/S007 evidence demonstrates pieces of these dimensions, not one real state where **two or more supported planner-visible actions simultaneously compete**.

## 3.3 Why R2 does not promote it yet

If the realistic supported policy reduces to:

```text
static authoritative contradiction first
else resolver
```

then deterministic sequencing is clearer and cheaper.

A model should not be inserted merely because “information value” sounds agentic.

Therefore the capability itself is independently justified, but **planner ownership of its selection remains unproven**.

## 3.4 Exact fresh evidence that would change the decision

R3 should look for a supported public Python dependency-update case with most of these properties:

1. declared/environment resolution is materially unresolved;
2. a bounded resolver/currentness check is genuinely useful;
3. at least one other independently useful read-only investigation is also available;
4. the better first action changes with trusted proposition state or prerequisite evidence;
5. always-resolve-first and always-static-first are both demonstrably wasteful/incomplete in some realistic states;
6. the distinction can be expressed without executing arbitrary target code.

A case with only one obvious unresolved resolver proposition is not enough.

### R2 disposition

**RETAIN FOR TARGETED R3 DISCRIMINATION — NOT YET A PLANNER ACTION.**

# 4. CAND-03 — mediated CI/environment-consumption hop

## 4.1 Strongest deterministic baseline

For a safely supported mediation family, deterministic evidence code can own:

```text
exact workflow declaration
→ exact statically referenced local/reusable config identity
→ fetch exact referenced source
→ bounded parser/interpreter for that admitted family
→ compose changed-dependency environment relation
→ supported | not_established | unresolved
```

with:

- finite depth;
- cycle detection where needed;
- no arbitrary target execution;
- exact source/revision lineage;
- unsupported syntax → unresolved.

This is ordinary evidence-graph expansion when references are structural and pre-bound.

## 4.2 S005 pressure does not yet prove planner selection

S005 establishes that a changed lock may be consumed through:

```text
uv.lock
→ tox environment
→ uv-venv-lock-runner
→ pytest
```

and that direct `uv sync` recognition is not enough.

But once the relevant tox/runner relationship is known, the case does not present several equally admitted mediation actions requiring model prioritization. The major missing product responsibility is **understanding the mediation path truthfully**, not choosing between several tools.

The accepted dependency-environment plan deliberately leaves generic tox/nox/Make/script interpretation outside its first support boundary. That is a scope/generality decision, not evidence that an LLM should interpret arbitrary task runners.

## 4.3 Why generic planner traversal is dangerous/weakly justified

A model-facing action like:

```text
inspect_another_relevant_config_file
```

would either:

- receive arbitrary file-selection authority; or
- rely on deterministic code already knowing the exact referenced source.

In the first form it is too broad.
In the second form the underlying acquisition is deterministic and the model may add no selection value.

If future cases expose many statically bound branches where selective expansion materially saves cost, planner value can be reconsidered. Current evidence does not establish that.

### R2 disposition

**DEMOTE FROM PLANNER CANDIDATE.**

Keep as a **separate deterministic evidence-capability gap** and as future hierarchical-planning pressure if later real cases demonstrate competing branches.

Do not search R3 primarily to rescue this candidate.

# 5. CAND-04 — target artifact/wheel-environment evidence

## 5.1 Strongest deterministic baseline

The earlier simulation-to-design handoff already answered the first acquisition question:

```text
exact repository + revision
→ one identified target environment/job
→ proposition-specific partial environment facts with provenance
→ enough facts for exact wheel compatibility?
    yes → TargetWheelCompatibilityEvidence
    no  → unresolved / insufficient
```

and recommended one statically readable GitHub Actions job as the first evidence family.

That design was later implemented in `target/artifact_environment.py` as a bounded deterministic interpreter.

Current implementation still has limitations:

- one safely selected local steps job;
- no generic matrix/expression evaluation;
- no reusable-workflow expansion;
- no broad runner-label → exact wheel-tag shortcut;
- no runtime environment claim.

These are honest product-support gaps, not evidence that a planner should choose the job.

## 5.2 Multi-environment repositories do not automatically justify LLM planning

The target-evidence handoff explicitly says:

```text
multiple legitimate environments
→ preserve environment identity
→ do not union them
```

For artifact serviceability, the owning proposition itself supplies useful deterministic filtering:

- removed/changed wheel compatibility family;
- target Python/platform/architecture evidence needed;
- exact workflow/job source.

A deterministic owner can enumerate/preserve candidate environment witnesses and evaluate them proposition-specifically. Missing matrix/reusable-workflow semantics belong to source/evidence interpretation.

The current evidence does not show that choosing among those witnesses requires semantic/planning judgment beyond deterministic proposition matching.

## 5.3 What future evidence could reopen planner value

Reconsider only if a real case demonstrates:

- several valid target-environment evidence sources;
- materially different acquisition costs/strengths;
- one source can settle the proposition while others are redundant;
- the best source changes with current trusted state/history/budget;
- deterministic filtering cannot remain small/general without encoding repository-specific policy.

No current case proves this shape.

### R2 disposition

**DEMOTE FROM PLANNER CANDIDATE.**

Retain target-environment acquisition as deterministic evidence work. It may later supply richer propositions/actions to a planner, but current evidence does not justify making its source selection model-owned.

## 6. Cross-candidate finding — capability authority and planning policy are separate

R2 reinforces a central architecture distinction:

```text
CAPABILITY EXISTS / IS WORTH BUILDING
!=
LLM SHOULD CHOOSE WHEN TO USE IT
```

Examples:

```text
resolver evidence
→ independently valuable missing proof rung
→ planner-selection value still unproven

mediated config tracing
→ independently useful product evidence gap
→ deterministic traversal/interpreter currently better owner

target environment acquisition
→ already justified deterministic responsibility
→ no evidence for model-owned source selection
```

This distinction prevents both under-engineering and agentic overreach.

## 7. Cross-candidate finding — model reasoning value may emerge from composition, not one tool

The first S001 seam had one action whose selector is deterministic.

R2 suggests that genuine planner value, if it exists, is more likely to appear when **several already-justified capabilities coexist** and the system must reason about:

```text
which proposition matters for the bounded question?
which evidence source can actually discriminate it now?
which action is prerequisite to another?
which action became stale/redundant?
which result has already consumed the action?
which check is worth its cost under the remaining budget?
when does stronger evidence make deeper work unnecessary?
```

This means the research should not force planner value into the internal semantics of each capability.

## 8. R3 targeted research question

R2 does **not** authorize random fresh-case hunting.

The exact targeted discovery question is:

> Can we find real public supported-boundary Python dependency-update cases where a resolver/currentness investigation and at least one other independently justified read-only investigation are both plausible, and where the correct order/selection changes with proposition state, prerequisite evidence, attempt history, or bounded information value?

Secondary screening signals may include:

- optional extras/groups plus lock/resolver state;
- coordinated package families;
- multiple platform/environment witnesses;
- artifact availability/serviceability questions coexisting with resolution questions;
- static metadata that may prune a resolver;
- exact config/source acquisition that may be prerequisite to a meaningful resolver scope.

Do not accept a case merely because it contains `uv.lock` or a failing resolver.
