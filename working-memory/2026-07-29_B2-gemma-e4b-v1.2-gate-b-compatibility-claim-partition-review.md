The failure is **not** that Gemma missed the compatibility assurance. It extracted the required claim correctly, then emitted one additional claim with an invalid category/change-state pair.

## Exact source and output

Source:

```text
This release remains backward compatible with the previous patch release and requires no migration.
```

Required minimum result:

```text
state: resolved
one compatibility_assurance / compatibility_assured claim
exact grounding
zero unresolved reasons
```

Observed output:

```text
claim 1: compatibility_assurance / compatibility_assured
claim 2: support_boundary_change / compatibility_assured
```

The first claim satisfies the intended oracle. The second claim is invalid because `support_boundary_change` permits only `support_added` or `support_dropped`.

## What the reasoning shows

The preserved reasoning correctly recognized:

- explicit backward compatibility;
- explicit absence of required migration;
- `resolved` as the overall state;
- `compatibility_assurance` as the correct category for the main proposition.

It then treated `requires no migration` as a second decision-relevant assertion and searched for another category, despite the v1.2 contract already defining absence of required migration as evidence for `compatibility_assurance`.

This produced an over-extracted second claim rather than a misunderstanding of the main assurance.

## Contract boundary exposed

State contract v1.2 defines valid categories and the compatibility meaning, but it does not explicitly define how several clauses in one sentence should be partitioned into claims.

For UpgradePilot, the selected representation is:

> Emit one claim per distinct supported category/change-state proposition, not one claim per clause. Clauses that jointly support the same proposition are combined into one claim.

For the failed sentence:

```text
remains backward compatible
+ requires no migration
→ one compatibility_assurance / compatibility_assured proposition
```

`requires no migration` is supporting evidence for the compatibility assurance. It is not a support-boundary change.

## Alternatives considered

### A. Reject Gemma and move directly to Qwen

Cost: treats a narrow and prompt-addressable claim-partition ambiguity as a general model failure before testing the missing contract.

Decision: not selected yet.

### B. Deterministically discard invalid extra claims

Cost: could silently hide model over-extraction and allow a partly wrong response to appear successful.

Decision: rejected for this stage.

### C. Add a minimal claim-partition contract and rerun only the failed case

Benefit: isolates the missing representation rule while preserving the model, schema, taxonomy, source, oracle, runtime, and validators.

Decision: selected.

## Selected contract v1.3 addition

Append only:

```text
Claim partition contract version 1.3: Emit one claim per distinct supported category and change-state proposition, not one claim per clause or phrase. When multiple clauses in one source span jointly support the same proposition, combine them into one claim. “Backward compatible” and “requires no migration” jointly express one compatibility_assurance with change_state compatibility_assured. Absence of required migration is never a support_boundary_change. Do not emit an extra claim merely to restate evidence that supports an already represented proposition. Before returning JSON, ensure every claim uses a valid category/change-state pair.
```

No category, change state, schema field, authority rule, grounding rule, model setting, or product behavior changes.
