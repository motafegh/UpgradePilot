## 1. Question answered

Stage 2 audited what evidence could actually demonstrate UpgradePilot value beyond the four-input transparent baseline, whether the prepared feasibility plan asks the right question, which retained scenarios/experiment results are valid development evidence, and whether another semantic/model/agent investment is currently justified.

## 2. Main conclusions

1. **Keep the product-value-first strategic direction.** Repeated semantic/model tuning on exposed Investigator fixtures is not the default next route.
2. **The original S001–S006 deep universe was too chronology-shaped.** S007–S016 contain materially distinct product responsibilities that can change the investment decision.
3. **Do not benchmark all sixteen.** Use S001–S016 only as a light screening universe, then choose the smallest discriminating deep cohort by responsibility, evidence mode and current producer/consumer reachability.
4. **Proof modes must remain distinct:** fresh end-to-end product, offline replay, deterministic component evaluation, current-source projection and historical manual/AI-assisted simulation are not interchangeable.
5. **Information value and action permission are separate.** Current synthesis admits only `abstain`; useful supported findings/uncertainty can still add product value, but abstention alone is not superiority.
6. **S001–S016 are exposed development evidence, not protected qualification.** Future generality claims after material tuning need newly protected material.
7. **Another semantic experiment requires a residual semantic question.** Deterministic/state/provenance/applicability gaps exposed by later cases may have cheaper existing owners.
8. **Bounded multi-role decomposition is a candidate only.** It is worth testing only if responsibility isolation is the actual residual hypothesis; earlier staged Fixed work is counterevidence to assuming more stages solve the problem.
9. **Semantic adequacy is material-premise based, not citation-cardinality based.**
10. **A complete findings contract cannot self-authorize Build/inference/execution.**

## 3. S001–S016 screen result

The screen found a useful evidence split:

- **S001–S006:** explicit historical `BASELINE_RESULT.json` artifacts; S003 is outside supported Python coverage; S006 has disclosed oracle/exposure limitations.
- **S007–S014:** materially distinct historical/manual pressure evidence, but not turnkey current-product/baseline pairs.
- **S015–S016:** explicit current-source projections for marker applicability and uv selected-scope behavior, but projections are not fresh product runs.

Likely discriminating roles, subject to deep readiness, include:

- S004 as baseline-sufficient/no-added-value control;
- S002 or S005 for false reassurance/coarse baseline miscalibration;
- S001 for supported upstream/target-applicability information;
- S015 or S016 for current deterministic transfer/boundary pressure;
- optionally S008/S011/S012 if a reachable current owner can consume their retained facts without manual oracle injection.

No cohort was frozen by this audit.

## 4. Correction performed

The existing [product-value feasibility plan](../plans/PRODUCT_VALUE_AND_TRANSPARENT_BASELINE_FEASIBILITY_INVESTIGATION_PLAN.md) was revised in place rather than creating a competing plan.

The revision:

- replaces fixed S001–S006 deep inventory with S001–S016 light screen → smallest discriminating deep cohort;
- preserves the six-active-engineering-hour total and zero model/GPU/network/target/benchmark allowance;
- makes evidence/evaluation mode first-class;
- separates information value from action permission;
- replaces citation-list adequacy with material-premise semantic adequacy;
- adds bounded multi-role interpretation/validation and materially different deployment/model tests as distinct conditional alternatives;
- preserves deterministic producer/projection/source-relation alternatives;
- requires explicit acceptance before a findings/action contract can authorize execution;
- keeps all historical simulation/experiment evidence immutable.

The October 20 review patch notes are therefore materially incorporated into the owning plan on this branch, with AUDIT-014's additional proof-mode and action/value corrections.

## 5. Verification
