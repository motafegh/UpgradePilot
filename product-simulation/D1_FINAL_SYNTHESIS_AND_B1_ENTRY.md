## 3. Minimum credible runtime responsibility candidate

B1 should freeze the smallest executable responsibility that can:

1. accept one real-shaped supported Python Dependabot case or replay fixture;
2. create a stable run identity distinct from invocation;
3. resolve and freeze repository, PR, base, head, changed-file, dependency, and version identity;
4. record material operations and evidence states with provenance;
5. preserve observations separately from interpretations and findings;
6. execute a versioned transparent baseline from restricted inputs;
7. represent dependency role/path and CI authority at the depth supplied by the fixture;
8. conditionally activate only the investigation responsibilities required by evidence;
9. select a bounded action or abstention with reasons and limitations;
10. produce machine and human reports from the same trusted decision state;
11. preserve follow-up, rerun, supersession, and changed-boundary transitions;
12. validate structural identity and lineage invariants;
13. expose review, assistance, and ownership state without claiming target safety.

B2 does not need live GitHub/PyPI acquisition, a database, services, agents, models, queues, graphs, or deployment infrastructure. It may begin from replay fixtures derived from the completed cases.

## 4. Universal responsibilities

Repeated evidence supports these as part of the minimum core:

- invocation distinct from discovered identity;
- exact frozen change identity;
- operation history;
- evidence records with explicit accepted, missing, inaccessible, expired, failed-method, partial, conflicting, or superseded states;
- evidence-to-interpretation-to-finding lineage;
- transparent baseline result;
- bounded decision, limitations, and confidence;
- machine and human projections;
- follow-up/new-run/supersession transitions;
- review and ownership separation;
- conditional-stage activation state;
- structural validation;
- immutable or recoverable source references;
- no target mutation by default.

## 5. Conditional responsibilities

Do not make these universal pipeline stages:

- advisory and exploitability analysis;
- adapter/framework compatibility;
- upstream activation-condition mapping;
- dynamic or isolated reproduction;
- repeated/matrix execution comparison;
- causal failure attribution;
- private or credentialed acquisition;
- native/platform/compiler analysis;
- post-merge publication/deployment evidence;
- dedicated stopping/cost artifact;
- separate dependency-update and PR-action decision dimensions.

The runtime must be able to represent their activation or non-activation. B2 does not need to automate all of them.

## 7. Baseline doctrine

The transparent baseline remains necessary because it provides:

- a reproducible comparator;
- evidence that repository-specific work adds value, adds no value, or overreaches;
- a way to detect action changes and calibration changes;
- a cost/stopping reference;
- protection against evaluating the full method only on explanation quality.

The baseline is not the product decision engine. S004 and S005 jointly show why:

- S004: baseline action can be sufficient;
- S005: baseline action can be too cautious and wrong.

The runtime must preserve both results without forcing the full method to win.

## 8. Decision model

A credible decision is not a static label. It includes:

```text
frozen case identity
+ bounded current action or abstention
+ evidence-backed reasons
+ limitations and uncertainty location
+ required checks, if any
+ transition conditions
+ supersession/new-run boundary
+ human review authority
```

The broad action set remains:

- merge after normal review;
- run targeted checks;
- investigate or block;
- defer;
- abstain.

Separate dependency and PR dimensions remain conditional, not universal.

## 9. Stopping model

Stop when no remaining evidence question can materially change:

- the broad action;
- uncertainty location;
- required checks;
- activation of a conditional responsibility;
- the product model or evaluation conclusion.

Non-activation is a result. Additional capacity is not a reason to continue.

## 10. Automation boundary at B1 entry

### Deterministic or strongly deterministic candidates

- identifiers and frozen identity;
- simple version and lock mutations;
- baseline execution;
- record creation and reference validation;
- workflow/job/step/command extraction from supplied evidence;
- matrix execution representation;
- report rendering from accepted application state;
- transition/state-machine mechanics.

### Tool-assisted or interpretive

- dependency path and role beyond simple declarations;
- CI responsibility and authority;
- upstream activation-condition extraction;
- target relevance and negative-evidence sufficiency;
- failure attribution;
- proportionate action selection;
- stopping and cost/value judgment.

### Human controlled

- target mutation;
- residual-risk acceptance;
- repository policy;
- final review and override;
- architecture and method admission;
- capability assessment.

B2 should implement deterministic state and invariants first while allowing prepared interpretations/findings as fixture input where semantic automation is not yet admitted.

## 11. Candidate B2 shape

The smallest credible executable flow after B1 acceptance is:

```text
replay fixture
→ validate invocation and frozen identity
→ create run and operation history
→ load evidence records and states
→ apply prepared or deterministic transformations
→ construct findings
→ execute transparent baseline
→ select bounded decision through an inspectable rule boundary
→ render machine and human reports
→ create follow-up transitions
→ validate lineage and state
```

The fixture must not supply an unexplained final decision. It may supply captured evidence and explicitly labeled prepared interpretations while B2 focuses on complete runtime state and invariants.
