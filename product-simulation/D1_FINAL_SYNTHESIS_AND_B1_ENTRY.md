## 3. Accepted minimum runtime responsibility candidate

B1 must freeze the smallest executable responsibility that can:

1. accept one real-shaped supported Python Dependabot replay fixture;
2. create a stable run identity distinct from invocation;
3. resolve and freeze repository, PR, base, head, changed-file, dependency, and version
   identity;
4. record material operations and evidence states with provenance;
5. preserve observations separately from interpretations and findings;
6. execute a versioned transparent baseline from restricted inputs;
7. represent dependency role/path and CI authority at the depth supplied by the replay;
8. conditionally activate only the responsibilities required by evidence;
9. select a bounded action or abstention with reasons and limitations;
10. produce machine and human reports from the same accepted state;
11. preserve follow-up, rerun, supersession, and changed-boundary transitions;
12. validate structural identity and lineage invariants;
13. expose review, assistance, and ownership state without claiming safety.

B2 does not initially require live GitHub/PyPI acquisition, persistence, services,
agents, models, queues, graphs, or deployment infrastructure.

## 4. Universal responsibilities

Accepted as recurring minimum-core responsibilities:

- invocation distinct from discovered identity;
- exact frozen change identity;
- operation history;
- evidence records with explicit accepted, missing, inaccessible, expired,
  failed-method, partial, conflicting, stale, and superseded states;
- evidence-to-interpretation-to-finding lineage;
- transparent baseline result;
- bounded decision, limitations, and confidence;
- machine and human projections;
- follow-up, new-run, and supersession transitions;
- review and ownership separation;
- conditional-stage activation state;
- structural validation;
- immutable or recoverable source references;
- no target mutation by default.

## 5. Conditional responsibilities

Do not make these universal stages:

- advisory and exploitability analysis;
- adapter or framework compatibility;
- upstream activation-condition mapping;
- dynamic or isolated reproduction;
- repeated or matrix execution comparison;
- causal failure attribution;
- private or credentialed acquisition;
- native, platform, or compiler analysis;
- post-merge publication or deployment evidence;
- dedicated stopping or cost artifact;
- separate dependency-update and PR-action decision dimensions.

The runtime must represent activation and non-activation. B2 does not need to automate
all conditional responsibilities.

## 6. Artifact conclusions

Repeated logical responsibilities include narrative/live view, manifest, invocation,
identity, operations, evidence, interpretations, findings, baseline, decision, reports,
follow-up, review/ownership, raw references, validation, and checkpoint history.

These are logical responsibilities, not accepted physical files or fields.

Conditional stable candidates:

- `CHECK_EXECUTIONS.jsonl` — useful in S003 and S005 for material execution comparisons;
- `FAILURE_ATTRIBUTION.json` — useful in S003 for competing causes;
- `STOPPING_EVALUATION.json` — useful in S004 when sufficiency and cost were the case
  question.

## 7. Baseline doctrine

The transparent baseline remains necessary as a reproducible comparator for:

- action changes;
- same-action authority improvements;
- sufficiency and stopping;
- calibration changes;
- cost and over-investigation.

It is not the final decision engine:

- S004 showed it can be sufficient;
- S005 showed it can be too cautious and wrong.

The runtime must preserve both outcomes without forcing the full method to win.

## 8. Decision and stopping models

A credible decision includes:

```text
frozen identity
+ bounded action or abstention
+ evidence-backed reasons
+ limitations and uncertainty location
+ required checks, when applicable
+ transition conditions
+ new-run or supersession boundary
+ human review authority
```

Stop when no remaining evidence question can materially change the action, uncertainty
location, required checks, conditional activation, or product/evaluation conclusion.
Non-activation is an affirmative result.

## 9. Automation boundary at B1 entry

Strong deterministic candidates:

- identifiers and frozen identity;
- simple version and lock mutations;
- transparent baseline execution;
- record creation and reference validation;
- workflow/job/step/command extraction from supplied evidence;
- matrix execution representation;
- report rendering from accepted state;
- transition mechanics.

Tool-assisted or interpretive:

- complex dependency role and path;
- CI responsibility and authority;
- upstream activation-condition extraction;
- target relevance and negative-evidence sufficiency;
- failure attribution;
- proportionate action selection;
- stopping and cost/value judgment.

Human controlled:

- target mutation;
- residual-risk acceptance;
- repository policy;
- final review and override;
- durable method and architecture admission;
- capability assessment.

B2 should implement deterministic state and invariants first while allowing explicitly
labeled prepared interpretations where semantic automation is not yet admitted.

## 10. Candidate B2 flow

```text
replay fixture
→ validate invocation and frozen identity
→ create run and operation history
→ load evidence records and states
→ apply prepared or deterministic transformations
→ construct findings
→ execute transparent baseline
→ select bounded decision through an inspectable boundary
→ render machine and human reports
→ create follow-up transitions
→ validate lineage and state
```

A fixture must not supply an unexplained final decision.
