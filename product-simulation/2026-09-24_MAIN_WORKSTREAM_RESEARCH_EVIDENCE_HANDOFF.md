## 1. Decision-relevant result in one paragraph

The real cases support separating **Command-Derived Requirement-State Proof** (exact applicable requirement + admitted effective pip/uv semantics + exact successful occurrence → satisfied at that command's completion) from **Direct Target-Owned Package-State Observation** (package/version observed in an identified target environment at an identified time). Neither route proves how the other worked; neither automatically proves **later use**. The next design decision is therefore not whether every install needs a redundant inventory: it is which *positive interpreter/destination/environment-identity and, only for stronger later-use claims, time/continuity/consumption relationships* can be supported in ordinary real CI. The main's current source-backed [Python environment-identity investigation](../working-memory/2026-09-24_python-environment-identity-evidence-investigation.md) already owns that open question; our cases provide validation and constraints, not a competing architecture.

**Cross-case proof boundary:** [what/where/when/exercise synthesis](2026-09-24_STATE_PROOF_ROUTES_WHERE_WHEN_AND_EXERCISE_CROSS_CASE.md) distinguishes: (a) requirement satisfied in E at command C completion; (b) package/version observed in E at T; (c) version present for a later consumer X; (d) that version actually used, and (e) changed behavior exercised. A sufficient (a) witness needs no mandatory later inspection for **the same** (a) claim. To assert (c)–(e), establish the *additional* material same-environment, ordering, continuity, actual-use and behavioral evidence; keep missing edges unresolved.

## 3. Broader reality checks: observed mechanism versus unsupported bridge

- **[G1 command/runtime](2026-09-22_G1_COMMAND_RUNTIME_REAL_CASE_SCREENING.md):** Aruba #83 shows a sole direct-source install and an actually executed later sequential install evidenced by its *own log*. Successful enclosing step alone must not be generalized into execution of every inner command. aiohttp #13785 exposes a different upstream gap: `pip -c` constrains requested packages, unlike `-r`, and current direct-requirements source recognition does not simply admit the changed constraints file. Source consumption must be proved, not guessed.
- **[G2 exact job composition](2026-09-22_G2_MULTI_JOB_TARGET_FIRST_SCREENING.md), [controls](2026-09-22_G2_NONCONSUMER_CONTROL_AND_STOP.md):** distinct static jobs and matrix rows are not interchangeable target environments. An unrelated successful job does not prove the changed dependency; a matrix-expanded runtime row is not itself a new static job key. No suitable full contrasting real case was confirmed in that bounded screening; controlled variant designs are *synthetic*, not runtime evidence.
- **[G3 ambient semantics](2026-09-22_G3_REALITY_CHECK_AMBIENT_SEMANTICS.md):** real public CI uses literal package-manager env, shell-local constraint exports, and simple `GITHUB_ENV` propagation of `PIP_CONSTRAINT` / `UV_NO_SYNC`. But exact `PIP_DRY_RUN` workflow examples, *same-variable double* `GITHUB_ENV` writes, and same-variable propagated-then-step-env collision were **not observed in the bounded searches/samples**. That is neither impossibility nor population prevalence. Prioritize observed, consequence-bearing families; preserve cheap fail-closed correctness without letting synthetic-only cases alone demand universal environment emulation. File-level co-occurrence does **not** prove a value reached a specific process.
- **[Retargeting check](2026-09-22_RETARGETING_REALITY_CHECK.md):** real `pip --target/--user/--prefix` patterns occur; selected Dependabot controls used retargeted tooling commands **unrelated** to the exact changed-dependency consumer. No clean supported-update case yet binds `changed source → retargeted consumer → later target environment/use`. Retargeting is a *destination-identity relationship*, not an automatic blacklist or grounds for a universal resolver.
- **[G4 compatible-tag feasibility](2026-09-22_G4_EXACT_WHEEL_TAG_WITNESS_FEASIBILITY.md):** TileDB-Py runs `pip debug --verbose` in distinct OS/Python matrix rows and emits different exact compatible-tag sets; runner/Python labels are not equivalent. No verified *same-revision supported dependency update + exact tag-witness* bridge was found in the bounded follow-up. Relevant to a later Target/wheel-evidence owner, **not** an automatic requirement for the active package-state subsystem.
- **[uv marker-order pressure](2026-09-22_UV_RESOLUTION_MARKER_ORDER_REALITY_CHECK.md):** a real Thumbor lock update has resolution-marker list-order changes that current canonical extraction may treat as ambiguity. Whether normalizing that order is semantically valid remains **unresolved**; do not call it harmless or change extraction without an authoritative semantic/real-case justification.

## 4. Questions still unresolved for the main owner

1. **Normal environment identity:** For each candidate proof route, what *positive* evidence binds the exact package-manager or inspector **process** to its actual interpreter, installation/inspection destination, and the selected dependency-consuming environment? Matching source paths, package/version text, job label, or a bare `python` command alone are insufficient. The current main [environment-identity investigation](../working-memory/2026-09-24_python-environment-identity-evidence-investigation.md) additionally reports that path-qualified `.venv/bin/python -m pip install` and `pip --python` are not presently admitted by the pip-prefix parser. **Do not describe them as current product-positive witnesses.**
2. **Execution and timing:** If a direct observation occurs later in a multi-command step, what exact evidence proves that observation *executed*, came from the intended process, and belongs to the stated run attempt/job/environment? Current step-success correlation is bounded; source-visible inspection text is not itself observed state. When does later use actually need continuity checks rather than a redundant inventory?
3. **Manager-specific supported boundary:** Which normal pip/uv command, process-local env, config and destination shapes can be closed positively without a full shell/runner emulator? Treat a no-sync/constraint/retargeting value as dimension- and claim-relative, not one global `safe/unsafe` flag.
4. **Evidence acquisition/retention:** Which target-owned structured version/inventory facts are already emitted and attributable in supported real updates? Logs or artifacts unavailable after retention must stay `unavailable`, not become negative state. Selecting a direct-observation adapter is still an owner decision.
5. **Scope and priority:** How often are the currently unobserved B4 collision families decision-relevant *inside UpgradePilot-supported updates*, and what is the cheapest sound unresolved/fail-closed response? Do not infer prevalence from GitHub code-search file counts or from a handful of examples.

## 5. Bounded design / verification implications (not architecture decisions)

- Keep the two candidate proof sources separate in **what, where, when, how known, and proof limits**; they may support suitably scoped downstream state facts independently. A direct observation never retroactively proves command semantics or installation provenance.
- Reuse already modeled exact dependency identity, selected-root reachability, command occurrence, and run/job correlation instead of rebuilding them. Extend evidence only where a real **missing relation** is demonstrated (notably effective interpreter/destination identity and a direct observation's exact executed occurrence).
- Preserve `unresolved` for missing premises, inapplicable requirements, unproven environment equality, expired evidence, and later-state gaps. An invalid positive command witness does not prove absence; a positive state witness does not prove compatibility or maintainer-action permission.
- Turn S013–S016 into **transfer/regression questions** only when the main owner selects an implementation slice; research has not run UpgradePilot end-to-end on these PRs and does not claim that they currently pass or fail as product tests.
- Ask of any proposed additional witness: **which new claim would it establish beyond the nearest already sufficient witness?** Do not require a second inspection merely to restate proven command-completion state. Test decision-criticality against the bounded maintainer action, not an unlimited completeness goal.
