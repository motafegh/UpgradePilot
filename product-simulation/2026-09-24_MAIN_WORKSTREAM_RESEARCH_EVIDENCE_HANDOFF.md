The [cross-case synthesis](2026-09-24_STATE_PROOF_ROUTES_WHERE_WHEN_AND_EXERCISE_CROSS_CASE.md) separates: (1) requirement satisfied in environment E at command C completion; (2) package/version observed in E at time T; (3) that version present for later command X; (4) X actually uses it; (5) changed behavior exercised. An already sufficient command-completion witness does **not** require a redundant inventory for the **same** claim. Claims crossing into later time/environment/use require their own positive links.

## Broader reality checks and unresolved bridges

- **[Exact command and source (G1)](2026-09-22_G1_COMMAND_RUNTIME_REAL_CASE_SCREENING.md), [job/target controls (G2)](2026-09-22_G2_NONCONSUMER_CONTROL_AND_STOP.md):** A later internal install may be evidenced by its **own retained log**, not merely an enclosing green step. The exact changed source, consuming occurrence, static job key, and applicable runtime/matrix row cannot be substituted with a convenient neighboring command/job. The aiohttp constraints example exposes a distinct `-c` source-relation question; `-c` must not simply be reclassified as `-r`.
- **[Ambient-semantics reality check (G3)](2026-09-22_G3_REALITY_CHECK_AMBIENT_SEMANTICS.md):** Real workflows use literal environment controls, shell-local constraint exports, and simple `GITHUB_ENV` propagation of `PIP_CONSTRAINT` or `UV_NO_SYNC`. Exact `PIP_DRY_RUN` workflow examples, same-variable double `GITHUB_ENV` writes, and same-variable `GITHUB_ENV`→step-env collisions were **unobserved in bounded screening**, not disproved. File-level keyword co-occurrence is not proof of receipt by an exact pip/uv process. Prioritize observed, consequential cases without sacrificing cheap fail-closed correctness.
- **[Retargeting](2026-09-22_RETARGETING_REALITY_CHECK.md):** `pip --target/--user/--prefix` occurs in real CI; screened Dependabot examples retargeted **tooling unrelated to the changed dependency**. The needed bridge—exact changed-dependency consumer → actual install destination → relevant later inspection/use—is still unverified. Retargeting requires positive environment-identity evidence, not a blanket rejection or universal resolver.
- **[Exact wheel tags (G4)](2026-09-22_G4_EXACT_WHEEL_TAG_WITNESS_FEASIBILITY.md):** TileDB-Py demonstrates target-owned `pip debug --verbose` compatible-tag evidence across OS/Python matrix rows. A single matching-revision *supported dependency-update + tag witness* case is not yet verified. Route this to the later Target/wheel-evidence owner, not as a mandatory package-state subsystem feature.
- **[uv resolution-marker list ordering](2026-09-22_UV_RESOLUTION_MARKER_ORDER_REALITY_CHECK.md):** Real upstream lock changes can trigger an extraction ambiguity. Whether normalization preserves uv fork semantics remains **unresolved**; route to the lock-extraction owner rather than silently normalizing.

Search-hit counts and small selected samples are **not prevalence estimates**. A synthetic counterexample proves possibility, not implementation priority; lack of a found case does not prove impossibility. Evidence from expired job logs must remain unavailable, not negative package-state evidence.

## Decisions this evidence can inform now — without deciding for main

1. **Supported environment identity:** Which ordinary, positively established process/interpreter, package destination, and target-owned observation facts bind each proof source to the selected dependency-consuming environment? The current [main investigation](https://github.com/motafegh/UpgradePilot/blob/main/working-memory/2026-09-24_python-environment-identity-evidence-investigation.md) notes that path-qualified `.venv/bin/python -m pip install` and `pip --python` are **not currently admitted** by the pip-prefix parser; they must not be presented as existing end-to-end positive product evidence.
2. **Execution and observation:** What proves that the **exact** inspection occurrence ran and produced its output in that run attempt/job/environment? Current step-success strengthening does not establish every later internal command. Direct state observation does not retroactively prove an installation command's semantics.
3. **Claim-relative continuity:** For a later-use claim only, what positive same-environment, ordering, material intervening-mutation, and actual-consumption facts connect earlier state to later execution? Keep missing links unresolved, not package absence or compatibility.
4. **Proportional coverage:** Which normal pip/uv semantic/retargeting/configuration dimensions are decision-critical in supported updates, and which unobserved edge shapes can stay explicitly unresolved? Avoid both an isolated flag-only patch and an unsupported universal CI/shell emulator.

**Handoff disposition:** Use S013/S014 and S015/S016 now as discriminating controls for the candidate two-proof-source design; use G1/G3 and retargeting when reviewing exact execution and environment identity; retain G4 and lock-marker ordering for their respective later owners. Treat all cases as **research/evaluation evidence**, not product regression tests already run end-to-end. The target repositories were read-only; this handoff neither edits `main` nor authorizes Build, a branch merge, or external target actions.
