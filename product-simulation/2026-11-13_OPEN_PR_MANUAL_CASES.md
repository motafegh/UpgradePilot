## How to use the packs

Start with the repository and PR number from `CASE_EVIDENCE.json` for each future ordinary CLI investigation. Keep the manual conclusions on the evaluation side. Before using a later live result in the comparison, check the base/head and exact run/attempt again. A changed observation belongs to its own evidence horizon.

Each `README.md` combines the case narrative, observed evidence, current-product stage results, historical transparent-baseline comparison, decision and stopping rationale. Each `CASE_EVIDENCE.json` combines the manual manifest, invocation, exact identities, selected steps, package observations, deterministic owner results and retained-source digests. This compact layout follows the later scenario precedent and keeps a reviewable record without recreating the historical D1 file set. Review and learner ownership remain pending. These are illustrative simulation artifacts.

The manual analysis used exact PR patch and CI REST observations, commit-pinned workflow and target source, public job pages and annotations, exact PyPI releases and publisher provenance, and tagged upstream notes. In response to the initial anonymous REST quota exhaustion, the GitHub PR and step pages supplied interim evidence. After the quota reset all four PRs and their captured attempts were checked through the REST route. The exact source inputs were read as data. The installed public CLI, model and target code were not executed. Current deterministic owners were used offline to verify the manually derived evidence boundaries. These checks exercise individual owners on retained inputs. They do not verify full public-CLI acquisition, report projection, or recovery for this cohort.

Reviewed derived facts and immutable source references are published here. Raw third-party responses, archives, wheel text and the focused check scripts remain private. ## What the cases discriminate

- **Execution and explanation.** ApplyPilot's failed consuming step and FalkorDB's skipped consuming step are materially different. Ask a reviewer to locate each first stop and state the strongest claim the evidence permits. The next unresolved premise in ApplyPilot is exact failure attribution. In FalkorDB the declared Python conflict can already be answered without any new run.
- **Local evidence inside a larger workflow.** MapProxy supplies positive evidence in both matrix tests and an ordinary coverage job. server-nexe supplies a positive ordinary job with an unrelated skipped sibling. Any design that relaxes workflow-wide matching must first show that it can preserve revision, event, attempt, job, and step identity, including duplicate names, conditions and ambiguous matrix expansion. The two cases support testing that narrower hypothesis. They do not select an implementation.
- **Independent artifact and semantic constraints.** Pyee and Soup Sieve have no wheel-tag delta but still have material dependency or behavioral evidence. Pandas has a Python metadata exclusion and a timestamp mechanism. Psutil has changed tags without an established exact target wheel loss. Keeping each proposition and its target scope visible is more useful than combining them into one compatibility score.
- **Usefulness criterion.** On the same frozen evidence, compare a later product report with the case's manually sourced answer. Check whether the reader can locate the first stop, name the strongest supported conclusion, and state a follow-up whose result would change their decision. A smaller report that answers these questions is sufficient. These exposed cases can guide development. Independent human usefulness requires a separate observation.
