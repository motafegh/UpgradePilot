# S020 — FalkorDB pandas update, Python setup and timestamp units

**Maintainer question.** Why did CI stop, would the proposed pin fit the declared Python environment, and what migration behavior should be checked after setup is repaired?

**Frozen case.** Open Dependabot PR #29, base `5033cecb19be9dd9393695a41b90c212a70943dd`, head `1f114dc971b29d6b93177c1bf8144078b2b7bb47`, observed November 13, 2026. The only changed file is `requirements.txt` with `pandas 2.2.3 → 3.1.1`. [PR](https://github.com/FalkorDB/migrate-neo4j-falkordb/pull/29/files) · [Evidence record](CASE_EVIDENCE.json)

## Observed evidence

1. Exact-head REST run `42609060595`, attempt 1, job `129132417413` failed at step 3, Python setup. The job annotation identifies the cause at the setup boundary. The runner could not find Python 3.9 for x64 Ubuntu 26.04. Step 4, the requirements install, and step 7, tests, were skipped. This run did not attempt to resolve pandas. The anonymous public step and job logs returned 404 and 403, but the job annotation gives the setup reason. [Workflow](https://github.com/FalkorDB/migrate-neo4j-falkordb/blob/1f114dc971b29d6b93177c1bf8144078b2b7bb47/.github/workflows/ci.yml#L10-L40) · [CI job and annotation](https://github.com/FalkorDB/migrate-neo4j-falkordb/actions/runs/42609060595/job/129132417413)
2. **Independent of the observed setup failure, the proposed pin conflicts with the workflow's declared Python 3.9.** Published pandas metadata moves from `>=3.9` to `>=3.11`. Old and proposed releases publish 41 and 57 wheels respectively plus one sdist each, but the new release has zero CPython 3.9 wheels. The full tag delta is 39 removed and 57 added. On a normal Python 3.9 install, the new release's Python metadata excludes both wheel and source routes. Repairing runner availability while preserving Python 3.9 therefore leaves a distinct incompatibility. The target did not provide a top-level `pyproject.toml` or `setup.py` at this head. The finding is scoped to the declared CI path. [Old metadata](https://pypi.org/pypi/pandas/2.2.3/json) · [New metadata](https://pypi.org/pypi/pandas/3.1.1/json)
3. **Fixing Python may expose a second, application-level problem.** The migration exports timestamps by calling `pd.to_datetime(...).astype("int64") // 1_000_000` in two paths. Pandas 3.0 changes ordinary parsed timestamp resolution from nanoseconds to microseconds when the input precision allows it. Integer conversion preserves that unit, so the same division can give an epoch value 1,000 times smaller, aside from rounding. This is a source-grounded applicability candidate for affected inputs. No migration or pandas execution was performed. The target README describes microseconds while the old nanosecond-plus-division expression produces milliseconds. Establish the intended unit from the downstream contract before proposing a code change. [Migration expressions](https://github.com/FalkorDB/migrate-neo4j-falkordb/blob/1f114dc971b29d6b93177c1bf8144078b2b7bb47/migrate/export_from_neo4j.py#L37-L69) · [Target unit description](https://github.com/FalkorDB/migrate-neo4j-falkordb/blob/1f114dc971b29d6b93177c1bf8144078b2b7bb47/README.md#L100-L110) · [Tagged pandas release notes](https://github.com/pandas-dev/pandas/blob/3dcc6fbbbebc5e85dd3e83fe49b382ca7735cae1/doc/source/whatsnew/v3.0.0.rst#L433-L507)

## Baseline, next check and stop

The transparent baseline sees failing CI and a major update and returns `investigate_or_block` under B01. It does not locate the setup stop or expose the Python-floor and timestamp risks. [Baseline](../../TRANSPARENT_BASELINE_SPECIFICATION.md)

The maintainer first needs to decide whether the target will retain Python 3.9 or move to 3.11+. The existing pin and workflow cannot satisfy both. If upgrading Python is intended, verify the intended timestamp unit, then compare old and proposed pandas on a representative CSV value in a common supported interpreter. Check dtype, integer representation and the exported value. A green setup or an install success would leave this behavior question open. The frozen source archive contains no `tests/` files, and the workflow's pytest command includes a shell fallback that can mask nonzero exit. A generic green rerun would therefore have limited value without an explicit timestamp assertion.
