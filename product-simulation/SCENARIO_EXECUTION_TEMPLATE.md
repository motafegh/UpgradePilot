# 1. Why this case was selected

Describe:

- why this is a real and useful dependency-update case;
- which current uncertainty, thesis claim, assumption, artifact need, or coverage
  dimension it tests;
- how it differs materially from completed scenarios;
- why it is not a duplicate case;
- known access, legal, reproducibility, timing, or raw-preservation limits;
- what would make the case no longer worth continuing;
- which baseline behavior the case may challenge.

# 2. Initial real-world event

Describe what happened before UpgradePilot begins:

- update producer;
- repository and proposed change visible to the maintainer;
- PR/update state;
- visible CI, review, bot, or package information;
- what is known to the user but not supplied to the system;
- what user decision currently needs support.

# 3. Intended invocation

Record only what UpgradePilot actually receives at the beginning. Materialize the
same state in `artifacts/INVOCATION.json`.

| Item | Value | Supplied/generated by | Purpose | Required/conditional/optional | Missing/wrong consequence |
|---|---|---|---|---|---|

Distinguish:

- caller-supplied values;
- event-supplied values;
- generated runtime metadata;
- browser-visible but not supplied information;
- policy or authorization context;
- unknowns before acquisition.

Do not insert discovered evidence or semantic answers into invocation input.

# 4. Case identity and reproducibility boundary

Freeze and materialize `artifacts/CASE_IDENTITY.json`.

Potential identity elements include:

- repository and PR/change reference;
- base/head branch and full revision;
- dependency/ecosystem;
- old/new versions or constraints;
- changed files;
- update producer;
- creation, update, close, merge, or supersession times;
- relevant workflow run or artifact identity;
- investigation observation time.

Explain:

- authority for each identity;
- which values were discovered rather than supplied;
- later-state evidence and how it is labeled;
- exact reproducibility boundary;
- what cannot be reproduced;
- whether a rerun requires a new `run_id`.

# 12. Repository-specific relevance

Explain how the dependency and proposed changes matter—or do not matter—to the
exact target snapshot.

Potential dimensions:

- declared directness;
- resolved dependency path;
- selected groups/extras/markers;
- functional use;
- build/test/runtime role;
- deployment installation;
- source/configuration path;

# 25. Artifact and progressive-record validation audit

A scenario cannot be marked complete until all applicable items pass.

## Bundle existence and identity

- [ ] `RUN_MANIFEST.json` indexes every logical artifact.
- [ ] Invocation and frozen identity remain distinct.
- [ ] Scenario, run, repository, and revision identities are consistent.
- [ ] Missing/not-applicable/unrecoverable artifacts are explicit.

## Progressive execution

- [ ] Initial selected/frozen checkpoint exists.
- [ ] At least one material investigation checkpoint exists before completion.
- [ ] Operation order is honest and not reconstructed as artificially perfect.
- [ ] Every material step has question, method reason, expected output, actual
      result, outcome, and next action.
- [ ] Failed/replaced/superseded paths remain visible.

## Evidence and lineage

- [ ] Every material evidence item has a producing operation or explicit imported
      origin.
- [ ] Raw/reference provenance is sufficient and honest.
- [ ] Evidence states remain distinct.
- [ ] Claims/interpretations identify actor and transformation.
- [ ] Findings reference evidence and interpretations.
- [ ] Decision reasons reference findings or explicit limitations.
- [ ] Reports match the current decision and limitations.

## Machine validation

- [ ] Every JSON file parses.
- [ ] Every non-empty JSONL line parses independently.
- [ ] IDs are unique.
- [ ] Cross-artifact references resolve or are explicitly external.
- [ ] Manifest inventory matches actual files.

## Baseline and thesis

- [ ] Baseline version and restricted inputs are recorded.
- [ ] Baseline rules were not changed during the case.
- [ ] Full comparison is complete.
- [ ] The result does not assume the full investigation must outperform.

## Review and ownership

- [ ] Execution, factual review, Ali review, and external evaluation are separate.
- [ ] Human/AI attribution is honest.
- [ ] Ali capability is not inferred from approval or AI generation.
- [ ] Corrections and disputes remain visible.

## Stop quality

- [ ] Further work stopped only when it no longer changed the decision, limitation,
      product/artifact understanding, method assessment, or replay value enough to
      justify cost.
- [ ] No unsupported safety, completeness, production, or ownership claim appears.
